## 1. Диагностика: что именно было сломано

Гипотеза задания («#93 отключил физику целиком, поэтому узлы не двигаются») оказалась
**наполовину верной**. Замеры до правки (`window.__intState`, реальные drag/pan/zoom
события мыши в Playwright):

| Вкладка | Узлов | Drag | Pan | Zoom | Physics после загрузки |
|---|---|---|---|---|---|
| Добавки между собой | 11 | **сломан (0 px)** | ✅ работает (130 px) | ✅ работает | `false` |
| Добавки и лекарства | 46 | **сломан (0 px)** | ✅ работает (130 px) | ✅ работает | `false` |

**Сломано было только перетаскивание узлов. Пан и зум не были сломаны ни разу.**

Настоящая причина — не отключённая физика, а `fixed: true`, который #93 ставил на
**каждый** узел при подстановке предрасчётных координат:

```js
return Object.assign({}, n, {
  x: p.nx * cw, y: p.ny * ch, fixed: true
});
```

vis-network не двигает зафиксированный узел ни мышью, ни пальцем. Узлы визуально
стояли на месте, владелец видел «граф статичен» и отнёс это ко всей интерактивности,
хотя панорамирование и зум продолжали работать. Замер: смещение узла при drag = 0 px,
`fixedNodes = 11` / `46`.

Вторая половина гипотезы подтвердилась: `physics.enabled` действительно вычислялся как
`!(fixedCount > 0 && fixedCount >= filtered.nodes.length)`, то есть при полном покрытии
координатами физика выключалась совсем. Обе причины исправлены.

### Важное уточнение по стеку

В задании предполагался d3 (`alphaDecay`, `alphaMin`, `d3.drag`, `d3.zoom`).
Фактически граф построен на **vis-network 9.1.9** (`docs/vendor/vis-network-9.1.9.min.js`).
Эти параметры к нему неприменимы; аналоги — `physics` + `interaction`. Хэндлеры drag
и pan никуда не девались после #93: `interaction` содержит `dragNodes: true`,
`dragView: true`, `zoomView: true`, они и работают — блокировало именно состояние узлов.

## 3. Что сделано

### 3.1 Узлы больше не фиксируются

`fixed: true` убран. Предрасчётные координаты теперь **стартовая точка** раскладки,
а не её результат:

```js
return Object.assign({}, n, { x: p.nx * cw, y: p.ny * ch });
```

Это ключевая правка: именно она возвращает drag. Раскладка стартует осмысленной
(`graph_positions.json`, layouts `interactions_supplements` / `interactions_drugs`),
поэтому симуляция лишь додавливает её, а не раскладывает 121 узел с нуля — то есть
причина зависания, которую чинил #93, не возвращается.

`fixedCount` переименован в `posCount` и оставлен как диагностика: сколько узлов
стартовало не с нуля (11 и 46 — то есть файл позиций отдаётся штатно).

### 3.2 Физика включена в обеих вкладках + cooldown по времени

```js
const PHYSICS_COOLDOWN_MS = 2000;
```

```js
physics: { enabled: true, solver: 'barnesHut', /* параметры прежние */ stabilization: false, ... }
```

Сразу после `new vis.Network(...)`:

```js
clearTimeout(state.cooldownTimer);
state.cooldownTimer = setTimeout(function () {
  state.cooldownTimer = 0;
  state.cooldowns++;
  try {
    if (state.network) state.network.setOptions({ physics: { enabled: false } });
  } catch (e) { /* сеть могли пересоздать между тиком и вызовом */ }
}, PHYSICS_COOLDOWN_MS);
```

`clearTimeout` обязателен: `drawGraph()` зовётся на каждый ввод в поиск и на смену
фильтра severity, и старый обработчик иначе выстрелил бы в уничтоженную сеть.

### 3.3 Почему cooldown, а не `stabilization.iterations`

Первая попытка была логичнее всего — ограничить бюджет итераций штатным механизмом
vis-network:

```js
stabilization: { enabled: true, iterations: 80, updateInterval: 25, fit: false }
```

**Она зависла.** `waitForFunction(physicsEnabled === false)` истёк по таймауту 25 с.
Причина найдена в вендоренном исходнике (`vendor/vis-network-9.1.9.min.js`),
`_finalizeStabilization()`:

```js
...!0 === this.stabilized ? this._emitStabilized() : this.startSimulation()
```

По исчерпании `iterations` виз-сеть **не останавливается, а перезапускает
неограниченную симуляцию** — ровно то зависание, которое чинил #93. Поэтому
ограничение сделано по времени, снаружи симуляции. В коде оставлена предупреждающая
комментария, чтобы эту ошибку не повторили.

### 3.4 Drag- и pan-хэндлеры

Править не потребовалось и не потребовало: `dragNodes: true` / `dragView: true` /
`zoomView: true` были и остались, но были заблокированы состоянием узлов. Проверено,
что конфликта drag узла и pan фона нет: dragStart/dragEnd вызываются только когда под
курсором узел, иначе кадр тянется (view).

### 3.5 Чего не трогали

Вкладки «Механизмы», «Тренды», BI, пайплайн данных и снапшоты — без изменений.
Дифом затронут один файл.

## 9. Как проверять руками

1. Открыть «Взаимодействия» → вкладка «Добавки между собой».
2. Первые ~2 с узлы слегка «дышат» — идёт раскладка от предрасчёта, потом замирают.
3. После замирания: тянуть узел — едет и тянет рёбра; тянуть пустое место — едет кадр;
   колесо — зум. Всё доступно в любой момент.
4. Вкладка «Добавки и лекарства»: то же самое, страница не подвисает.

## 10. Что осталось на заметку

- `PHYSICS_COOLDOWN_MS` — единственное ограничение физики. Если когда-нибудь
  понадобится другая длительность, менять нужно только его; `stabilization.enabled`
  в этой виз-сети ограничителем не является (раздел 3.3).
- `fixedCount` → `posCount` — переименование публичного поля в `window.__intState`.
  На тесты не влияет, но если где-то есть внешний скрипт/консоль, который читает
  `fixedCount`, он перестанет видеть число.
