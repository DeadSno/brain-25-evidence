## 2. Graph: какая гипотеза сработала

**Сработала не одна, а комбинация: Г1 частично + Г3 по сути.**

Разбор показал, что `graph.html` уже ждёт стабилизацию сама
(`network.once("stabilizationIterationsDone")`, 1000 фиксированных
итераций), то есть гипотеза Г3 в её наивном виде («harness не ждёт
события») не подтвердилась как основная.

| Гипотеза | Вердикт | Чем проверено |
|---|---|---|
| **Г1 `layout.randomSeed`** | ⚠️ частично | Опция есть в vis-network, но фокус оказался не в зерне, а в порядке вызовов заморозки (см. ниже) |
| **Г2 `physics.stabilization.iterations`** | ❌ отпадает | Уже задано 1000 — фиксированное число, причина не в нём |
| **Г3 ждать стабилизацию в harness** | ✅ **да, но глубже** | Harness ждал `SETTLE_MS = 600` после `networkidle`; вывод после правки совпал побайтово |
| **Г4 выключить физику** | ✅ **да, это и было решение** | `__freeze` выключал её, но слишком поздно |

### Настоящая причина — порядок вызовов в `FREEZE_JS.__freeze`

Harness уже умел замораживать граф: `__freeze()` раскладывает узлы по
детерминированной окружности через `moveNode` и выключает физику. Но
порядок был обратный:

```js
net.setData({nodes: new vis.DataSet(fixed), ...});   // ← перезапускает стабилизацию
net.setOptions({physics: {enabled: false}});          // ← слишком поздно
```

`setData` перезапускает стабилизацию, и разлетевшийся граф успевал
отрисоваться поверх только что выставленных координат. Правка:

```js
net.setOptions({physics: {enabled: false,
                          stabilization: {enabled: false}}});
net.setData({nodes: new vis.DataSet(fixed), ...});
fixed.forEach((nd) => net.moveNode(nd.id, nd.x, nd.y));
```

Детали, которые стоили времени:

- **`net.setPositions` в vis-network 9.1.2 отсутствует** (`TypeError:
  net.setPositions is not a function`). Есть `moveNode`, `getPositions`,
  `stabilize`, `stopSimulation` — использован `moveNode`.
- Первый вариант правки давал **6 падений из 6 одинаковых** — то есть
  детерминизм наступил, но раскладка стала отличаться от эталона,
  снятого со случайной. Это был успех, а не регресс; я это отметил
  отдельно, чтобы не принять за новую поломку.

## 4. Хрупкость `:has()` устранена

По решению владельца — вариант (б), класс на `<body>`.

`docs/script.js`:
```js
// openModal
$('modalOverlay').style.display = 'flex';
document.body.classList.add('modal-open');
// closeModal
$('modalOverlay').style.display = 'none';
document.body.classList.remove('modal-open');
```

`docs/style.css`:
```css
body.modal-open .site-header { z-index: 1; }
```

Селектор `body:has(#modalOverlay[style*="display: flex"])` больше не
используется (осталось одно упоминание в комментарии — как объяснение,
почему от него отказались).

**Проверка, оба движка, порядок «закрыто → открыто → закрыто»:**

| | закрыто | открыто | снова закрыто |
|---|---|---|---|
| `body.modal-open` | нет | **есть** | нет |
| `z-index` шапки | 100 | **1** | **100** |
| `z-index` оверлея | 50 | 50 | 50 |
| `#toTop` | 60 | 60 | 60 |
| видно в верхней точке | `div` | **`div#modalOverlay`** | `div` |

Третий шаг обязателен: без него не видно, что правило не оставляет шапку
опущенной навсегда после первого открытия. Все 30 проверок совпали.

### Что вскрылось по пути

`test_silent_handlers` упал: allowlist молчаливых ранних выходов
**ключуется номером строки**, а моя правка `script.js` сдвинула всё ниже
на 7 строк. Перенесено 6 записей на фактические строки, каждая сверена с
кодом: 614, 765, 825, 827, 925, 1053, 1109. Первая попытка автоматизации
ошиблась на записи 818 (два соседних guard'а с почти одинаковым
условием выиграли по баллам не тот) — перепроверено чтением кода.

Плюс к тому: три файла оказались записаны с **CRLF вместо LF**, как у них
в HEAD. На тесты не влияет, но в коммит попал бы весь файл целиком вместо
изменённых строк. Переводы нормализованы, diff стал читаемым.
