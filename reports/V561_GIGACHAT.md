## 3. Второе стоп-условие: `opencode.json` vs `opencode.jsonc`

README и `docs/CONFIGURATION.md` требуют глобальный конфиг
`~/.config/opencode/opencode.json`. У вас такого файла **нет вообще**:

```
opencode.jsonc            11687 байт   ← единственный рабочий
opencode.jsonc.bak         2242 байт
opencode.jsonc.bak-serena  1870 байт
```

Создавать второй глобальный конфиг без согласования запрещено условием
задачи, поэтому я не стал.

**Проверено отдельно:** Desktop 2.0.24 грузит все три возможных пути — в
логе видны `config.json`, `opencode.json` **и** `opencode.jsonc`. То есть
провайдера технически можно было бы добавить в существующий `.jsonc`, без
второго файла. Но это расходится с буквой README, поэтому вынесено
вопросом; вы отложили его до решения по A1.

## 4. Отдельно: `"provider"` или `"providers"`

Это расхождение я нашёл, проверяя доки V2, и считаю важным отметить.

README плагина и его CONFIGURATION.md пишут **`"provider"`** (единственное
число) — это форма V1.

Документация **V2** (<https://opencode.ai/v2/docs/providers>) требует
**`"providers"`** (множественное). Проверено по странице: в примерах
встречается только `"providers":`.

То есть даже если бы совместимость с v2 подтвердилась, конфиг плагина в
реализации V2 может оказаться в неверном разделе. Это ещё один аргумент
не ставить вслепую. Дополнительно: сам блок `agents` с V2-`permissions`
уже ломал V1 CLI в прошлой задаче — конфиг этой машины обслуживает
**два рантайма** (Desktop 2.0.24 V2 и CLI 1.18.33 V1), и любая V2-конструкция
здесь потенциально конфликтует с V1.

Ничего не скачано и не установлено. Если решение изменится, порядок
должен быть таким (по README, а не по задаче):

1. закрыть OpenCode;
2. скачать `gigachat-plugin.js` из v1.0.2;
3. `mkdir -p ~/.config/opencode/plugins` и положить файл;
4. добавить провайдера в **существующий** `.jsonc` (не создавать `.json`);

   у моделей добавить `modalities`; лимиты взять из CONFIGURATION.md;
5. `opencode providers login --provider "GigaChat (Sberbank)"`,
   scope `GIGACHAT_API_PERS`, ключ Base64 из кабинета Sber Developers;
6. перезапустить Desktop и проверить модель + MCP.

Перед шагом 4 стоит убедиться, что V2 вообще примет форму
`{ provider, loader, methods: [{ type: "api" }] }` — иначе плагин
молча не даст авторизацию, и диагностика уйдёт в сторону TLS.

## 7. Вопросы владельцу

**1. Ставить на свой страх после вердикта «v2 не указан»?** Сейчас решение
«не ставить». Если хотите проверить вживую — минимальный безопасный шаг:
поставить файл плагина и провайдера **без** авторизации и прочитать
журнал загрузки (`--print-logs`): подхватил ли Desktop 2.0.24 плагин и не
упали ли MCP. Это обратимо и не требует ключа.

**2. `"provider"` или `"providers"`?** README плагина говорит `provider`,
доки V2 требуют `providers`. Я не могу выбрать за вас — это ровно тот
случай, где README и документация V2 противоречат друг другу, и задача
запрещает угадывать.

**3. Нужен ли GigaChat вообще?** Плагин неподдерживаемый (README прямо),
прототипный, под v2 не проверенный, а текущая модель
`opencode/space-bunny-free` работает. Резервный канал уже есть —
`@azumag/opencode-rate-limit-fallback` с `longcat-2.5-preview-free`.
GigaChat дал бы независимость от внешних провайдеров и российский контур
(TLS-сертификаты Минцифры встроены), но ценой неподдерживаемости.

**4. Если GigaChat нужен для РФ-контура** — есть официальный путь без
плагина: OpenCode умеет `@ai-sdk/openai-compatible` напрямую с
`baseURL: https://api.giga.chat/v1`, где нужен настоящий OAuth-токен
Сбера, а не виртуальный адрес. Плагин удобен тем, что берёт на себя OAuth
и сертификаты, но это и есть его единственная добавленная ценность.
