# SNAPSHOT_MASK — маскировка версии в снапшотах

## 1. Harness

**Файл:** `tests/test_visual_snapshots.py`

**Места вызова скриншота:**
- Строка 499: `return page.screenshot(full_page=full_page)` — функция `_capture`, 72 теста
- Строка 634: `png = page.screenshot(full_page=False)` — тест `test_modal_index_snapshot`, 2 теста

**Всего тестов снимающих кадр:** 74 (18 страниц × 2 разрешения × 2 движка = 72 + 1 модалка × 2 движка = 2)

**Два режима full_page:**
- `full_page=True` — 72 теста (все страницы, оба разрешения, оба движка)
- `full_page=False` — 2 теста (модалка на index, оба движка)

**Другие файлы в tests/:**
- `test_snapshot.py` — не делает скриншотов, сравнивает JSON
- `test_ui_verify.py` — запускает `scripts/ui_verify.py` (e2e маркер, не snapshots)

## 2. Выбор способа маски

**Выбран вариант A — через `page.evaluate`:**

```python
page.evaluate(
    """() => {
        document.querySelectorAll('[data-version="app"]').forEach(el => {
            el.textContent = 'vX.X.X';
        });
    }"""
)
```

**Почему вариант A, а не B (mask= у page.screenshot):**

1. **Вариант A подставляет фиксированную строку**, а не розовый прямоугольник. Это честнее: пользователь видит настоящую версию, а в снапшоте — фиктивная строка, которая не меняется при смене версии.
2. **Вариант B рисует розовые прямоугольники по умолчанию** — это изменит эталон. Можно задать `mask_color` совпадающий с фоном, но это сложнее и менее надёжно (зависит от фона страницы).
3. **Вариант A работает одинаково для обоих режимов** (full_page=True и full_page=False), потому что маскирование происходит до вызова `page.screenshot()`.
4. **Вариант A проще в реализации** — не нужно передавать список локаторов в `page.screenshot()`.

**Проверка обоих вариантов:**
- Вариант A проверен на практике: после внедрения смена `app` с `5.6.1` на `5.9.9` не роняет тесты (73 passed, 1 skipped).
- Вариант B не проверен на практике, но теоретически должен работать. Однако он менее предпочтителен из-за розовых прямоугольников и сложности с `mask_color`.

## 3. Проверка

**Три прогона:**

| Прогон | Версия app | Результат | Примечание |
|--------|-----------|-----------|------------|
| 1 | 5.6.1 | 53 failed, 20 passed, 1 skipped | Эталоны содержат старую версию, маскировка заменяет на vX.X.X |
| 2 | 5.9.9 | 73 passed, 1 skipped | Маскировка работает — смена версии не роняет тесты |
| 3 | 5.6.1 | 73 passed, 1 skipped | Возврат к исходной версии, тесты проходят |

**Обоснование:**
- Прогон 1: после добавления маскировки эталоны содержат реальную версию `5.6.1`, а маскировка заменяет её на `vX.X.X`. Поэтому 53 теста упали (те, где версия видна в снимке).
- Прогон 2: после пересъёмки эталонов с маскировкой, смена версии на `5.9.9` не влияет на снимки, потому что маскировка заменяет любую версию на `vX.X.X`.
- Прогон 3: возврат к `5.6.1` подтверждает, что тесты проходят с исходной версией.

## 6. Вопросы владельцу

1. **Маскировать только `app` или все поля версии?**
   Сейчас маскируется только `[data-version="app"]`. Поля `data`, `audit`, `tests` не маскируются. Если они тоже будут меняться часто, можно добавить маскировку и для них.

2. **Значение для маскировки:**
   Сейчас используется `vX.X.X`. Можно использовать другое значение, например `v0.0.0` или `X.X.X`, если это лучше подходит для визуального тестирования.

3. **Маскировка в других тестах:**
   В `test_ui_verify.py` (e2e) тоже могут быть скриншоты с версией. Нужно ли добавить маскировку туда?

4. **Автоматическая пересъёмка:**
   Сейчас пересъёмка выполняется вручную через `UPDATE_SNAPSHOTS=1`. Можно ли автоматизировать этот процесс, например, через GitHub Actions?
