# Финальная зачистка перед merge v5.5.0

Ветка `v5.1-dev`. Продолжение `reports/DIAGNOSTIC_FIX.md`.

## Главное, что вскрылось

Отключение DuckDB MCP вернуло **16 молча пропускавшихся тестов**.

```
до:   755 passed, 18 skipped
после: 771 passed,  2 skipped
```

Причина в `tests/conftest.py:153`: при ошибке блокировки вызывается
`pytest.skip("brain.duckdb занят другим процессом (MCP duckdb?)")`.
Пока MCP-сервер держал файл, шестнадцать тестов молча выпадали из прогона.
Судя по пометке «(MCP duckdb?)» в самом conftest, на эту причину уже
подозревали — но без отключения сервера проверить было нечем.

Это отдельный аргумент в пользу отключения: MCP-сервер не давал доступа
к своим инструментам, но молча отключал шестнадцать тестов проекта.

## Часть A — DuckDB MCP отключён

### A1. Какие конфиги существуют

| Путь | Есть | Размер | Роль |
|---|---|---|---|
| `~/.config/opencode/opencode.json` | нет | — | глобальный, не создан |
| `~/.config/opencode/opencode.jsonc` | **да** | 955 б | **активный глобальный** |
| `./opencode.json` | **да** | 627 б | проектный |
| `./opencode.jsonc` | нет | — | удалён в прошлом заходе |

По документации opencode глобальный конфиг выбирается как **первый
существующий** из `opencode.jsonc` → `opencode.json` → `config.json`,
поэтому активен `opencode.jsonc`. Проектные файлы, наоборот,
загружаются все сразу и объединяются — но в проекте остался только
`opencode.json`, так что объединения нет.

### A2. Правка внесена

Ключа `enabled` у duckdb **не было**. Добавлен первым в блоке — перед
`type`, по образцу уже отключённого exa:

```jsonc
"duckdb": {
  "enabled": false,
  "type": "local",
  "command": [...]
}
```

Конфиг проверен: JSON валиден, `duckdb.enabled = false`,
`exa.enabled = false`, `context7` и `playwright` без изменений.
Порядок ключей: `enabled`, `type`, `command`, `environment`.
BOM, CRLF и битых символов нет.

### A3. Проверка фактического эффекта

Перезапустить opencode сам не могу, но результат уже виден:

| Что | Состояние |
|---|---|
| процесс duckdb MCP (был PID 3448) | **завершён** |
| `data/db/brain.duckdb` | **открывается**, 8 таблиц, 162 МБ |
| инструменты duckdb в каталоге | 0 — сервера нет |
| playwright, context7 | работают |

Файл освобождён, и это подтверждено не списком процессов, а попыткой
открыть базу из Python. Перезапуск для окончательной проверки
`opencode mcp list` всё же нужен: сейчас сервер не запускается потому,
что процесс завершился, а не потому что прочитан обновлённый конфиг.
При следующем старте он запускаться не должен — иначе причина будет
в другом месте.

## Часть B — дубли playwright: найдены, но не убиты

### Что обнаружено

| Тип | Копий |
|---|---|
| `npx`-обёртки | 3 |
| сам MCP | 3 |
| **всего** | **6** |

Ожидается одна обёртка и один MCP. Суммарно ≈ **500 МБ**.

Все шесть стартовали в пределах 400 мс друг после друга, то есть
поднялись одновременно при старте, а не накопились за несколько
перезапусков. Состав процесса между проверками менялся сам: в одном
списке был PID 1780, в следующем его нет, появились 2532 и 2944.

### Почему я их не убил — отступление от B2

Задание предлагает `Stop-Process -Name node -Force`. Это сознательно
не сделано, и вот почему:

1. **Мой собственный инструмент playwright работает через один из этих
   процессов.** Убив их, я обрушу себе доступ к MCP посреди задачи.
2. **Они перезапускаются сами.** Состав процесса меняется без всякого
   вмешательства — opencode ими управляет. Убийство не даёт ничего:
   на место придут новые.
3. **Это не блокер merge.** 500 МБ оперативной памяти не влияют на
   содержимое репозитория и не попадают в поставку.
4. **Перезапуск всё равно нужен** для A3 — и он создаст процессы заново.

То есть правильное действие — не убивать, а отметить находку. Если
duplicates раздражают, вопрос к opencode: почему MCP поднимается трижды
при одном старте.
