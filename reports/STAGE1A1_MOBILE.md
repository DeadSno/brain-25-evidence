**`.site-header`: 134-182px → 118-136px, выигрыш −15…−46px.**

### 2.1 `.top` - цель достигнута

**`.top`: 79-84px.** Комментарий v5.6.2 (`docs/style.css:1289`) обещал «шапка
~90px вместо 419-511px» - **подтверждён**: 79-84px против ~90px.

### 2.2 Цель «весь `.site-header` <100px» - не достигнута

`.site-header` - не одна строка, а две стопки:

```
118.3 = trustbar 34.6 + padding-top 4.8 + site-title 27 + gap 8 + actions 44
```

- **`.trustbar` - 31-54px.** Отдельная полоса «🧬 Открытые данные · Бесплатно ·
  Без рекламы». На faq / sup-b1 / map текст встаёт в две строки → 53.8px.
  Собственного padding у `.site-header` нет (0px), margin `.top` схлопывается
  наружу.
- **`.top` - 79-84px** = title 27 + gap 8 + actions 44 + padding.

Дойти до <100px можно только структурно, и все три варианта - вне рамок
«минимальной правки CSS»:

1. **Скрыть `.trustbar` на ≤480px** → −31…54px → 79-84px. Но это удаление
   сообщения - продуктовое решение, не вёрстка.
2. **Свести title и actions в один ряд** - невозможно: контент `.actions` при
   nowrap равен 502-1566px против 312-341px доступной ширины.
3. **Ужать ниже 44px** - прямое противоречие цели 1A по tap-целям.

**Вывод: `.trustbar` на ≤480px - отдельная задача, не 1A-1.**

## 3. Замер B - `.actions` на 375px

| | baseline | после правки |
|---|---|---|
| Ширина контейнера | 341 / 328 / 322 | **341 / 328 / 322 - идентично** |
| `min-width` computed | `0px` | `0px` |
| Сжимающихся items | 0 | **0** |
| `white-space != nowrap` | все items | **0** |
| Сумма ширин items | 349 → 1158 | **502 → 1566** |
| Скролл внутри `.actions` | есть | **есть, by design** |
| Скролл страницы по X | нет | **нет** |

Всё сходится: контейнер равен ширине колонки и не может стать шире неё, но items
сохраняют **полную** ширину - контент вырос с 349 до 502px, потому что текст
перестал сжиматься внутри кнопки. Горизонтальная прокрутка живёт внутри
`.actions` (это и есть by design из медиазапроса ≤620px), страница по X не едет
ни на одной из 6 проверенных страниц.

## 4. `min-width:0` - страховка, пиксели не меняют на ≤620px

| | baseline | после правки |
|---|---|---|
| `min-width` на 320 / 480px | `0px` | `0px` |
| `min-width` на 768 / 1024 / 1280px | `auto` | `0px` |
| ширина `.actions` на 768 / 1024 / 1280px | 721 / 961 / 1152 | **721 / 961 / 1152** |
| page overflow | −15 | **−15** |

На ≤620px `min-width:0` **уже стоит** в медиазапросе (строка ~1290) - правило в
базовом слое там избыточно. Выше 620px контент помещается в колонку и
`min-width:auto` ничего не распирает. Итог: **ни одного изменившегося пикселя
ни на одной ширине.**

Оставлено сознательно: правило дешёвое, безвредное, синхронизирует базовый слой
с медиазапросом и защищает десктоп, если `.actions` когда-нибудь перестанет
помещаться. На удаление потребовался бы отдельный контрольный замер на десктопе.

```

opacity          : 1    → 0.8
matches(':active'): true
отпускание       : чистый возврат в none / 1
```

- Голый `<a>` в `<main>` остался `transform:none, opacity:1` - не затронут.

- `#cookieBanner` - это `div` со своим `transform:translateX(-50%)`; на
  `button:active` не попадает.

## 7. Ловушки, стоившие реального времени

Все три записаны также в `AUDIT_MASTER`:

1. **`git show HEAD:file > file` в PowerShell пишет UTF-16LE** (BOM 255,254) и
   удваивает файл: `style.css` 116046 → 235722 байт, CSS разваливается.
   Рабочее: `cmd /c "git show HEAD:docs/style.css > docs\style.css"` - побайтово
   точно. Проверка: `[System.IO.File]::ReadAllBytes($f)[0..3]`.
2. **CSSOM выкидывает комментарии.** `cssRules[].cssText` никогда не содержит
   текста комментария, поэтому проверка «применилась ли правка» через
   `cssText.includes('1A-1')` всегда даёт `false`. Проверять надо по реальному
   селектору: `.actions > *`, `button:active`.
3. **Кэш браузера съедал baseline.** Замеры «до» и «после» молча отдавали
   отредактированный CSS. `Network.setCacheDisabled` через CDP не помог.
   Помогло только **разделение по портам** - разный origin, разный кэш.
   Перед замером проверять скачиванием: длина и наличие селектора.
