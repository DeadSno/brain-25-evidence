# P0 — ДИАГНОСТИКА: `feedback.html` теряет сайт после отправки

Дата: 2026-10-01 · Ветка: `v5.0.0-dev` · Skill: `qa-dev`
Источник: находка P0 №1 из `reports/UI_UX_AUDIT.md`
**Задача — найти причину. Ничего не исправлялось.** `docs/`, `src/`, `scripts/`, `tests/` — чисто.

---

## Короткий ответ

**Причина найдена, воспроизводится 3 из 3.**

Форма делает **нативный POST на сторонний сервис** и уходит с сайта. Ключевая
строка — `docs/feedback.html:298`:

```js
if (errors.length) {
    e.preventDefault();      // ← вызывается ТОЛЬКО при ошибке валидации
    ...
    return false;
}
var btn = document.getElementById('f-submit');
btn.disabled = true;
btn.textContent = 'Отправляется…';
status.textContent = 'Отправляется…';
return true;                  // ← на успешном пути preventDefault НЕ вызывается
```

`preventDefault()` жив **внутри ветки ошибки валидации**. На успешном пути
обработчик просто возвращает `true`, поэтому браузер выполняет обычную отправку
формы на `action="https://api.web3forms.com/submit"`. Дальше документ покидает
наш домен — и что там отрисуется, решает Web3Forms, а не мы.

**Дополнение, которое и объясняет «иногда»:**
`Web3Forms` **игнорирует** поле `redirect` (`docs/feedback.html:172`) и отвечает
`200` со своей страницей `/submit/success` вместо `302` на наш URL. Поэтому
редирект на `feedback.html?ok=1` (код для него есть, строки 313-321) **не
срабатывает**, и пользователь остаётся на их странице.

## Доказательства

### 1. Разметка формы — нативный POST, а не fetch

`docs/feedback.html:167-172`:
```html
<form class="f-form" action="https://api.web3forms.com/submit" method="POST">
    <input type="hidden" name="access_key" value="9befbd42-…">
    <input type="hidden" name="subject"     value="Brain 25 Evidence — новое сообщение">
    <input type="hidden" name="from_name"   value="Brain 25 Evidence">
    <input type="hidden" name="redirect"    value="https://deadsno.github.io/brain-25-evidence/feedback.html?ok=1">
```

Ни `fetch`, ни `XMLHttpRequest`, ни `formaction` в файле нет — единственная
отправка это то, что браузер делает сам.

### 2. `defaultPrevented = false` на успешном пути — прямой замер

Слушатель `submit` на `document` (всплытие → срабатывает **после** их обработчика
на `.f-form`), значение выведено в Node через `exposeFunction` до навигации:

```json
{ "defaultPrevented": false,
  "action":  "https://api.web3forms.com/submit",
  "method":  "POST",
  "btn":     "Отправляется…",
  "disabled": true }
```

`defaultPrevented: false` — браузеру не запретили уйти.

### 3. Цепочка навигации

```
http://localhost:8000/feedback.html
  → https://api.web3forms.com/submit            POST   200
  → https://api.web3forms.com/submit/success    200
```
Финальный документ:
```
finalUrl      : https://api.web3forms.com/submit/success
hasHeader     : false
lang          : "en"
body text     : "Form submitted successfully! Thank you for reaching out to us.
                 We'll review your submission and get back to you soon.
                 Go Back — This form is powered by Web3Forms"
```

В ответе на `POST` нет заголовка `Location` — то есть редиректа на `redirect` не
происходит:
```json
{ "s": 200, "u": "https://api.web3forms.com/submit", "loc": null }
```

### 4. Вариативность исхода: 3 прогона из 3 одинаковые

| Прогон | Финальный URL | `hasHeader` | `lang` |
|---|---|---|---|
| 1 | `api.web3forms.com/submit/success` | false | en |
| 2 | `api.web3forms.com/submit/success` | false | en |
| 3 | `api.web3forms.com/submit/success` | false | en |

⚠️ **Прогон 2 из `UI_UX_AUDIT.md` не воспроизводится.** Там было
`header: true, footer: true` и ссылки `index.html`, `calculator.html`, «Web3Forms».
Наиболее вероятное объяснение — редирект на `redirect` **сработал один раз** и
браузер ушёл на **прод-домен** `deadsno.github.io`, который внешне неотличим от
локального (та же шапка, тот же футер со ссылкой на Web3Forms). Это гипотеза:
проверить её нельзя, не имея доступа к логам Web3Forms. Помечаю
«требует верификации», а не как факт.

**Практический вывод:** даже «удачный» исход — не наш успех. Пользователь
оказывается на чужом домене, просто не замечает этого.

### 5. Гипотеза пользователя — подтверждена наполовину

> Если `<form action="…">` без `e.preventDefault()` — нативный сабмит уводит на
> страницу Web3Forms.
> **✅ Подтверждено.**
> Если JS успел — preventDefault сработал. Если нет — уводит.
> **❌ Опровергнуто.** `preventDefault()` не вызывается **никогда** на успешном
> пути — это не гонка, а замысел. Момент выполнения JS ни при чём.

### 6. Гипотеза №5 из задания (гонка `initApp`) — опровергнута прямым тестом

**JS полностью отключён** (все запросы типа `script` → `abort`, новое окружение):

```
navChain   : localhost/feedback.html → api.web3forms.com/submit → /submit/success
finalUrl   : https://api.web3forms.com/submit/success
hasHeader  : false
lang       : en
```

Результат **тот же**. Значит скорость загрузки JS и успешность инициализации на
поведение не влияют вообще — это чисто серверная реакция Web3Forms.

### 7. Механизм успеха существует, но локально недостижим

Открыл прод-URL с флагом:
```
https://deadsno.github.io/brain-25-evidence/feedback.html?ok=1
→ hasSuccessBox: true
  text: "Спасибо! Ваше сообщение получено. Если указали email — отвечу в течение 2-3 дней."
  hasHeader: true
```

Код обработки `?ok=1` (`docs/feedback.html:313-321`) **работает**. Но поле
`redirect` — **абсолютный URL прод-домена**, поэтому с `localhost:8000` путь
«отправили → вернулись → увидели Спасибо» **невозможен в принципе**: браузер
всегда уходит на другой домен. Локально успех нельзя ни увидеть, ни
протестировать.

## Побочные находки (не P0, но в этом же коде)

### В-1. Собственные сообщения об ошибках недостижимы для пустых полей

`fStatus` при клике «Отправить» с пустыми обязательными полями — **пустая
строка**:
```json
{ "emptyRequired": { "status": "" } }
```

Причина: у полей стоит нативный `required`, браузер блокирует отправку **до**
события `submit`, и наш обработчик на `.f-form` просто не вызывается. Пользователь
видит только системный пузырь браузера, а не аккуратный текст проекта.

Собственные сообщения работают, но только для менее частого случая — значения
есть, но не проходят проверку:
```json
{ "tooShort": { "status": "Форма не отправлена: исправьте 2 пол.",
                "topicErr": "Укажите не менее 3 символов",
                "msgErr": "Сообщение должно содержать минимум 10 символов",
                "ariaInvalidTopic": "true" } }
```

**Вывод:** блок кода 264-304 написан грамотно (нет `alert()`, есть
`aria-invalid` и `role`-логика), но самый частый сценарий — пустое поле — до него
не доходит.

### В-2. Ключ `access_key` в исходнике

`docs/feedback.html:169`. Для Web3Forms это штатный режим (ключ публичный, иначе
без JS отправка невозможна), но стоит понимать: он виден любому посетителю и
позволяет слать форму от имени проекта.

### В-3. Ловушка `botcheck` не спасает при отключённом JS

`<input type="checkbox" name="botcheck" style="display:none">` — при выключенном
JS это обычная незаполненная галочка, уезжающая вместе с формой.

## Предлагаемый фикс (**НЕ применён**)

Основная проблема — не «баг Web3Forms», а то, что **мы отдали навигацию и
финальный экран чужому сервису**. Пока форма уходит через `action=`, сайт
не контролирует, что увидит пользователь.

### Вариант 1 (рекомендую): перехват через `fetch`, разметка состояний своя

Минимальные изменения, обратная совместимость полная:

```js
form.addEventListener('submit', async function (e) {
    e.preventDefault();                 // ← БЕЗУСЛОВНО, до любой валидации
    // ... существующая проверка полей ...
    btn.disabled = true;
    btn.textContent = 'Отправляется…';
    try {
        const r = await fetch(form.action, { method: 'POST', body: new FormData(form) });
        if (!r.ok) throw new Error(r.status);
        status.innerHTML = '<strong>Спасибо!</strong> …';   // по-русски, в нашей разметке
    } catch (err) {
        btn.disabled = false;
        status.textContent = 'Не удалось отправить. Проверьте соединение и попробуйте ещё раз.';
    }
});
```

Что это даёт: пользователь **не покидает сайт**, сообщение на русском, при отказе
форма остаётся и кнопка разблокируется, `?ok=1` больше не нужен.
Побочно: `access_key` перестаёт утекать в сеть при каждой отправке.

### Вариант 2: серверный редирект

Поставить свою страницу-обработчик (`/thanks`), которая делает POST на Web3Forms
и отдаёт `302` на `feedback.html?ok=1`. Тогда `redirect` не нужен, логика успеха
остаётся в нашем коде.

⚠️ Требует бэкенда; для статики на GitHub Pages не подходит.

### Вариант 3 (минимальный, если менять страшно)

Оставить нативный POST, но:
1. `redirect` сделать **относительным** (`feedback.html?ok=1`) — тогда редирект
   вернёт на текущий домен, и localhost начнёт работать;
2. добавить на их `/submit/success` нельзя — значит **гарантии не будет**: при
   отказе Web3Forms пользователь снова окажется на чужой странице.

Поэтому вариант 3 — только как временная мера.

### Отдельно: пустые обязательные поля (В-1)

Чтобы собственные сообщения показывались всегда, добавить на форму
`novalidate` и слушать `invalid` на полях, либо проверять на `submit` при
`novalidate`. Иначе половина написанной логики валидации недостижима.
