# SKILLS_AUDIT_ORION — аудит скиллов под мультиагентский режим

Дата: 2026-10-05 · Ветка: `v5.6-dev` (HEAD `6839c5a`, detached) ·
Режим проверки: Orion (`opencode-team-lead@1.0.0`, `opencode/space-bunny-free`)

## Главная находка: слой скиллов в мультиагентском режиме не работает

Ни один из 10 сабагентов Orion не может загрузить скилл. Проверено
не чтением конфига, а прогоном:

```
Orion → делегирует на security-reviewer
  «Load the cyberaudit skill…»
→ security-reviewer: ToolNotFound: the tool "skill" is not available
  to this agent. Available tools: read, glob, grep,
  list_mcp_resources, list_mcp_resource_templates, read_mcp_resource.
```

Сабагент **отказался отвечать по памяти** и вернул ошибку — поведение
правильное. Orion тоже не подменил работу собой.

Причина видна в `opencode agent list`: право `skill: allow` есть
**только у `team-lead`**. У всех десяти сабагентов набор инструментов —
`read / glob / grep / MCP`, без `skill`.

Следствие: 19 скиллов пригодны для первичных агентов и бесполезны для
сабагентов. А распределение по заданию (`data-audit → general`,
`accessibility-check → security-reviewer`, `cyberaudit → security-reviewer`,
`release-check → harness`) нерабочее — все четыре оборачиваются в
`ToolNotFound`.

**Обходной путь существует и проверен:** Orion сам загружает скилл
(`skill` ему доступен) и передаёт инструкции сабагенту в теле задачи.
Тест: `Skill "seo-check"` загрузился, ответил корректно. Но это ручной
режим, а не автоматический.

Этого пункта не было в ожидаемом списке задания (там ждали только
проблемы во frontmatter). Он важнее их всех вместе взятых и вынесен в
P0.

## 2. B1 — самодостаточность: ссылок много, битых нет

133 внешние ссылки в 13 скиллах. Все указывают на файлы внутри
репозитория, то есть доступны сабагенту через `read`.

**130 из 133 разрешаются.** Три «не найдено» оказались артефактами моего
же разбора, а не битыми ссылками:

| Ссылка | Что это на самом деле |
|---|---|
| `docs/X.md` (docs-sync) | плейсхолдер в таблице-примере `| docs/X.md | правка в Y.md | да |` |
| `tests/test_analyze_coi.py` (qa-deep-audit) | описание работы скрипта («готовит 5 XML-файлов»), а не ссылка на существующий файл |
| `docs/chore/test/ci/data` (release-check) | список типов коммита `feat/fix/docs/chore/test/ci/data`, склеенный регуляркой |

**Битых ссылок: 0.** Проверено `git ls-files` и разрешением путей.

Что действительно стоит поправить: почти все скиллы ссылаются на
`docs/dev/ROADMAP_NEW.md` и `reports/AUDIT_REPORT.md`. Это встроенный
контекст проекта, и он **протухает** — отчёт датирован 2026-09-30, а
проверки перечисляют файлы (`scripts/analyze_coi.py`), которые
существуют. Проблема не в битых ссылках, а в том, что сабагент,
загрузивший скилл, получает указание свериться с отчётом трёхнедельной
давности и принимает его за актуальное состояние.

Предложение: в скиллах, ссылающихся на `reports/*.md`, заменить
«сверься с отчётом» на «используй как базовую линию, актуальное
состояние проверяй сам», либо указывать дату отчёта прямо в тексте.

## 4. B3 — совместимость с Orion

### 4.1 `compatibility` (формально)

Есть только у `cyberaudit`, и это свободный текст:
`Pure Markdown skill, no external dependencies. Works with any AI agent
that loads SKILL.md.` — то есть «любой агент, который умеет грузить
SKILL.md», что верно, но не отвечает на вопрос «работает ли под
Orion-сабагентом». Отвечает: нет, см. 4.2.

### 4.2 Реальная совместимость (проверено прогоном)

| Агент | `skill` доступен | Проверка |
|---|---|---|
| `team-lead` (Orion) | **да** | загрузил `seo-check`, ответил верно |
| `security-reviewer` | **нет** | `ToolNotFound: the tool "skill" is not available` |
| остальные 9 сабагентов | **нет** | право `skill` в списке отсутствует |

Ожидаемое заданием распределение не работает:

| Маршрут из задания | Итог |
|---|---|
| `data-audit → general` | `general` без `skill` — не сработает |
| `accessibility-check → security-reviewer` | не сработает |
| `cyberaudit → security-reviewer` | не сработает (проверено) |
| `release-check → harness` | не сработает |

### 4.3 Что именно чинить

Не скиллы, а права. Два варианта:

**Вариант А — выдать `skill` сабагентам** в `~/.config/opencode/opencode.jsonc`:

```json
"agent": {
  "security-reviewer": { "permission": { "skill": "allow" } },
  "code-reviewer":     { "permission": { "skill": "allow" } },
  "review-manager":    { "permission": { "skill": "allow" } },
  "requirements-reviewer": { "permission": { "skill": "allow" } }
}
```

Риск: блок `agent` перекрывается catch-all заглушкой
`{"permission":"*","action":"deny"}` — её правило применяется
последним, как показал разбор прав Orion. Значит конкретное `allow`
надо ставить **после** заглушки, иначе оно не сработает. Требует
проверки на живой сессии.

**Вариант Б — грузить скилл в Orion, инструкции передавать сабагенту
в теле задачи.** Работает уже сейчас, проверено. Минус: Orion тащит
весь `SKILL.md` в свой контекст на каждой задаче и потом пересказывает.

Вариант А правильнее по смыслу, Б работает без правки конфига.

## 7. Вопросы владельцу

1. **Скиллы в мультиагентском режиме — как понимаем задачу?** Три
   варианта: (а) выдать `skill` сабагентам и грузить нативно;
   (б) оставить как есть и поручить Orion грузить и пересказывать;
   (в) сознательно не использовать скиллы сабагентами — тогда слой
   из 19 скиллов работает только на Orion и теряет смысл
   мультиагентской схемы. Я склоняюсь к (а), но порядок правил
   в конфиге требует проверки на живой сессии, а это уже за пределами
   read-only аудита.
2. **`cyberaudit` в объём работ не входит?** Он глобальный, в репозитории
   его нет, а пробелы в нём настоящие (нет `license`, нет
   рекомендаций). Правкой заниматься или оставить как есть?
3. **Протухшие отчёты в скиллах.** Ссылаться на `reports/AUDIT_REPORT.md`
   от 2026-09-30 как на источник истины — рабочая практика сейчас, или
   это то, что чинится пунктом 4?
4. **`compatibility` — писать во всех 18?** Поле информационное, плагином
   не читается, смысла в нём немного. Заполнить ради единообразия или
   не плодить ключи, которые ничего не делают?
