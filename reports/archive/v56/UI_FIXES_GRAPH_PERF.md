## 2. Переключатель темы на `interactions.html`

### Симптом

Клик по `#themeBtn` на `interactions.html` не переключал тему. На остальных
шести страницах тот же клик работал.

### Ход диагностики

`script.js`, где живёт обработчик темы для `index.html`, подключён только на
`index.html`. На остальных шести страницах обработчик свой, инлайновый.

| Страница | `script.js` | свой инлайновый обработчик | клик |
|---|---|---|---|
| index | да | да | работает |
| **interactions** | **нет** | **да** | **не работает** |
| atlas | нет | да | работает |
| map | нет | да | работает |
| calculator | нет | да | работает |
| trends | нет | да | работает |
| graph | нет | да | работает |

Два замера дали ложный след, и оба пришлось отбросить:

1. Инструментирование `DOMTokenList.prototype.toggle` показало **0**
   переключений класса `light`. Это не «setLight не вызвался» — инструментация
   была вставлена через `add_init_script`, то есть до загрузки страницы, и
   `document.documentElement` в замыкании указывал на объект, который
   страница потом пересоздавала. Замер ничего не доказывал.
2. Прямой вызов `setLight(true)` из консоли вернул
   `TypeError: Cannot read properties of null (reading 'classList')`. На
   повторном замере в чистом контексте тот же вызов отработал нормально, все
   семь элементов были на месте. Причина — инструментация предыдущего шага.

Что замер показал по-настоящему:

```
прямой dispatch b.onclick()  -> html='', localStorage.theme='dark'
setLight(true) напрямую      -> html='light', localStorage.theme='light'
```

То есть обработчик выполняется, класс ставится и тут же снимается.

### Причина

`docs/interactions.html:540`

```js
document.getElementById('themeBtn').onclick = () => setLight(!isDark());
```

`isDark()` возвращает «сейчас тёмная»:

```js
function isDark() { return !document.documentElement.classList.contains('light'); }
```

При тёмной теме `isDark()` = `true`, значит `!isDark()` = `false`, и
`setLight(false)` оставляет тёмную тему. Кнопка не переключала ничего: клик
по тёмной теме давал ровно то же состояние.

На `index.html` то же выражение выглядит иначе и работает:

```js
() => { const on = !document.documentElement.classList.contains('light'); setLight(on); ... }
```

Здесь `!contains('light')` и есть «переключаем в светлую». В `interactions`
эта логика попала под `isDark()`, который уже возвращает то же значение, —
инверсия удвоилась.

Комментарий в коде утверждал обратное («иначе клик был no-op»), то есть
код не делал того, о чём говорил комментарий.

### Правка

`docs/interactions.html:540` — аргументом стал сам `isDark()`:

```js
document.getElementById('themeBtn').onclick = () => setLight(isDark());
```

Тёмная → светлая, светлая → тёмная.

## 3. Офлайн-баннер

### Причина ложных плашек

`sw.js` шлёт `{type: 'offline'}` клиентам из двух мест — `sw.js:206` (упал
`fetch` данных) и `sw.js:274` (упал запрос статики). Но эти `catch`
срабатывают не только без сети: тот же путь даёт 404 постороннего файла,
таймаут опроса `data.json` с `cache: 'no-store'`, отказ CORS.

`pwa.js` реагировал на сообщение безусловно, поэтому плашка «Офлайн-режим:
данные могут быть устаревшими» появлялась при полностью рабочей сети.

### Правка

`docs/pwa.js:30` — признак один и проверяемый:

```js
function isReallyOffline() {
  return navigator.onLine === false;
}
```

- `showBadge()` выходит сразу, если сеть есть (гасит ложное сообщение `sw.js`);
- событие `offline` тоже сверяется с фактом;
- событие `online` гасит плашку, если факт уже изменился;
- автоскрытия через 5 секунд нет намеренно: офлайн сам не проходит, и
  исчезнувшая без причины плашка вводила бы в заблуждение сильнее, чем её
  отсутствие.

Промежуточная версия правки опрашивала `navigator.onLine` каждые 4 секунды
через `setInterval`. От этого отказались: события `online`/`offline`
браузер шлёт надёжно, а вечный таймер на каждой странице — постоянная
нагрузка ради страховки от события, которое и так приходит. Осталась
проверка по факту внутри обработчика.

### Проверка

| # | сценарий | ожидалось | факт |
|---|---|---|---|
| 1 | сеть есть, `sw` шлёт `{type:'offline'}` | плашки нет | нет, `onLine=true` |
| 2 | реальный офлайн | плашка есть | есть, `onLine=false` |
| 3 | возврат в сеть | плашка скрыта | скрыта |
| 4 | 7 секунд офлайна | плашка держится | держится |

Сценарий «открыть страницу уже офлайн» на стенде не воспроизводится:
`context.set_offline(true)` в Playwright рвёт и `localhost`, а service
worker в тестах заблокирован, поэтому кэшем его подставить нечем. Это
ограничение стенда, а не непроверенный код: путь `if (isReallyOffline())
showBadge()` при загрузке — это буквально последняя строка блока инициализации
(`docs/pwa.js:93`), и сценарий 2 проходит по тому же вызову.

Правка `pwa.js` первой попыткой внесла настоящую мозгибакку — два символа
U+FFFD в слове «послал» в комментарии. Поймал гард
`tests/test_no_mojibake_in_js.py`, символы заменены. Попутно устранён
дубль `badge = document.createElement('div')`, оставшийся от первой правки.

## 4. Предрасчёт позиций графа

### Что показал замер

Задача предлагала предрасчёт как «самый быстрый путь». Первая серия замеров
её предпосылку не подтвердила:

| страница | DCL | load | узлов | связей |
|---|---|---|---|---|
| interactions | 119 мс | 144 мс | 11 | 10 |
| atlas | 94 мс | 94 мс | — | — |
| graph | 89 мс | 95 мс | — | — |

Страницы открываются за 89–144 мс, и на `interactions` в режиме по умолчанию
всего 11 узлов. Вывод «оптимизировать нечего» был бы поспешным: DCL — это
время до отрисовки страницы, а не до готовности графа. `vis-network`
продолжает считать раскладку после загрузки.

### Настоящая проблема

Состав данных:

| файл | размер | узлов | связей |
|---|---|---|---|
| `graph_data.json` | 415 889 Б | 130 | 1 982 |
| `interactions_graph.json` (`supplements`) | 51 901 Б | 11 | 10 |
| `interactions_graph.json` (`drugs`) | — | 121 | 124 |

Время до события `stabilizationIterationsDone` на `graph.html`:

```
как есть                    до стабилизации: 21 229 мс
физика выключена            (стабилизации нет)
```

21 секунда при 130 узлах и 1 982 связях — вот чтоOptimизировать и стоило.
Страница при этом открывается за 74 мс, поэтому проблема и не была видна
при поверхностном замере.

### Раскладка

Силовая раскладка, посчитанная вне браузера, отвергнута: она зависит от
версии библиотеки и от зерна, а для снапшотного гейта нужна побайтовая
повторяемость кадра. Взята круговая раскладка в три концентрических кольца
(`_комментарий` в файле фиксирует решение).

Исходный JSON с узлами и связями **не тронут**. Позиции лежат отдельным
файлом `docs/graph_positions.json` (27 334 Б), координаты нормированы
(`nx`/`ny` в долях от 1), страница переводит их в пиксели под свой canvas.
Дублировать поля в исходных данных значило бы завести второй источник
правды, который разъедется.

Радиус ограничен `min(0.34 * scale, 0.94 * min(cx, cy))`. Первая версия
дала 11 узлов с координатами вне `0..1`: внешнее кольцо (`0.99` от базового
радиуса) выходило за верх и низ контейнера, потому что базовый радиус брался
от меньшей стороны, а по вертикали доступна лишь её половина.

Для `graph` нормализация идёт по размеру canvas (1078 × 766), а не по
высоте `#mynetwork` (800 px): из неё вычитаются 16 px отступов и 1 px рамки,
замерено в браузере. При нормировании по 800 крайние узлы уезжали за границу.

### Правки страниц

**`docs/graph.html`** — данные и позиции грузятся через `Promise.all`,
узлы получают `x`, `y`, `fixed: true`. Физика выключается условием
`"enabled": !(window.__posApplied > 0)`. Если файл позиций не загрузился
(404), физика остаётся включённой — страница работает, просто считает дольше.

**`docs/interactions.html`** — позиции подставляются в `drawGraph()` по
текущему режиму. Физика выключается, только если координаты получили **все**
узлы: `enabled: !(state.fixedCount > 0 && state.fixedCount >= filtered.nodes.length)`.
Частичное совпадение id оставило бы смешанную раскладку — часть зафиксирована,
часть считается.

В `state` добавлены поля `positions` и `fixedCount`, а также отладочная
ссылка `window.__intState`: `state` объявлен как `const` внутри скрипта, и
без неё проверить, сколько узлов зафиксировано и выключена ли физика, можно
было только по картинке.

**`docs/atlas.html` — не трогал, и вот почему.** `atlas` строит вершины
динамически из `data.json`: id дополнены префиксами (`tag:<название>`,
`sup:<id>`), а сами теги добавляются только при `tagCount >= 2`. Состав
видимых вершин меняется вместе с фильтром `activeTags`. Статический файл
позиций это не покрывает: набор вершин не фиксирован. Предрасчёт на `atlas`
возможен только при полном пересчёте под текущий фильтр — то есть это уже
не предрасчёт, а обычная раскладка на лету.

`interactions` для сравнения подходит: набор вершин фиксирован в JSON по
режимам, а поиск только прячет узлы полем `hidden`, не добавляя новых.

### Проверка

`graph.html`, три прогона:

| прогон | до стабилизации | физика | узлов | фиксированных |
|---|---|---|---|---|
| 1 | 0 мс | выкл | 130 | 130 |
| 2 | 0 мс | выкл | 130 | 130 |
| 3 | 0 мс | выкл | 130 | 130 |

Раскладка идентична во всех трёх прогонах (сигнатура первых 40 координат
совпала посимвольно). **21 229 мс → 0 мс.**

`interactions.html`:

| проверка | результат |
|---|---|
| режим `supplements` | 11 узлов, 11 фиксированных, физика выкл |
| переключение на `drugs` | 121 узел, 121 фиксированный, физика выкл |
| детерминизм, 3 прогона `drugs` | раскладка идентична |
| поиск «магний» | скрыто 114 из 121 узла, `hidden` работает |
| ошибки страницы | нет |
