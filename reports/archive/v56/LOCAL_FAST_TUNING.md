## 1. local-fast: read-only настроен, работает

### 1.1 Синтаксис правки

Пример из задания — `"permission": { "edit": "deny", "write": "deny" }` —
это **синтаксис V1**. V2 требует `permissions` (множественное) как
упорядоченный список `{action, resource, effect}`; документация V2 прямо
запрещает поле `permission`. Ровно этот случай уже описан в `AGENTS.md:7-12`.

Применено по V2:

```jsonc
"permissions": [
  { "action": "edit", "resource": "*", "effect": "deny" },
  { "action": "shell", "resource": "*", "effect": "deny" }
]
```

### 1.2 Найдена дыра в ограничении

Первая версия запрещала только `edit`. Проверка показала, что этого
**недостаточно**: получив отказ, модель переключилась на `shell` и
попыталась создать файл редиректом. Файл не создался — но не потому, что
запрет сработал, а потому что вызов ушёл текстом, а не структурным
вызовом. Вектор записи оставался открытым.

Подтверждение: агент **успешно выполнил `git --version`** и вернул реальный
вывод `git version 2.56.0.windows.2`. Значит `shell` был доступен.

После добавления запрета `shell`:

| Проверка | Результат |
|---|---|
| Чтение `docs/version.json` | ✅ вернул все 4 поля с верными значениями |
| Попытка `shell` | ✅ заблокировано — модель отступила и пошла читать файл |
| Файл от первой попытки записи | ✅ не создан |

**Вывод для документации:** запрет `edit` сам по себе read-only не
обеспечивает. Нужны оба правила.

### 1.3 Цена ограничения

`shell` отобран, и вместе с ним агент потерял `git log`, `git show`,
`rg` и прочие shell-команды. Для поиска остаются штатные инструменты
`glob`, `grep`, `read` — для задачи «поиск и разбор» их достаточно.
Цена осознанная: обход через `shell` работает.

Обе — по тексту задания, с добавлением проверенных фактов: запрет
`edit` не даёт read-only в одиночку; дело в базовой модели, а не в
Modelfile; побочный эффект — выдумывание имён инструментов.

### 2.2 Правка выполнена скриптом, а не через Edit

`Edit` не нашёл текст с кириллицей — **ровно та ловушка, что описана в
самом `AGENTS.md:90-92`**. По действующему правилу («не повторяй ту же
попытку, замени по номерам строк скриптом») вставка сделана скриптом
по точному совпадению строки `## LSP`.

### 2.3 Побочный эффект скрипта — пойман и исправлен

`read_text()` / `write_text()` на Windows конвертируют `\n` в `\r\n`.
Файл перешёл с LF на CRLF: 195 строк с CRLF. Git это нормализует при
индексации, поэтому `diff` оставался чистым, и без отдельной проверки
расхождение прошло бы незаметным.

Исправлено возвратом к LF. Проверка: **CRLF = 0**, предупреждение git
исчезло.

## 4. Качество local-fast: оценка

### 4.1 Что работает

| Задача | Результат |
|---|---|
| Прочитать **один известный файл** и извлечь поле | ✅ 6 из 6 прогонов безупречно |
| Соблюсти формат ответа | ✅ |
| Отреагировать на запрет и не настаивать | ✅ |

Все успешные прогоны в предыдущих отчётах были вертикальными: известный
путь, одно поле, одно значение.

### 4.2 Что не работает

| Задача | Результат |
|---|---|
| Обойти 90 файлов, найти кандидатов, дать ссылки `файл:строка` | ❌ 6 из 8 ложных, 3 физически невозможны |
| Отличить конфиг от форматирования | ❌ 1 из 2 верных — ложноположительная |
| Оценить объём работы | ❌ не оценивала |

### 4.3 Механизм отказа

Модель **не читала файлы**, а сгенерировала правдоподобный список.
Признаки видны в структуре ответа: единообразные «файл:строка:значение»,
уверенные пояснения, ссылка на несуществующие `git_version()` из
предыдущего прогона. Прямо спросить нельзя — агент отвечает, а не
проверяет себя.

### 4.4 Вердикт

**Оценка 3 из 10.** Надёжен для точечного чтения по известному пути.
**Непригоден** для анализа по репозиторию, где нужны ссылки на строки.

Причина структурная: модель 7B без достаточного grounding'а
достраивает правдоподобное вместо проверяемого. Наблюдение в
`AGENTS.md` про выдумывание имён инструментов — тот же механизм.

**Это не повод отказываться от агента** — он остаётся полезным там, где
задача сводится к чтению. Но задачу из блока C ему отдавать нельзя.
