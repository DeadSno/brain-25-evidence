# LOCAL_DELEGATION — проверка tool calls у локальной модели и настройка subagent

**Дата:** 2026-10-07
**Ветка:** v5.6-dev
**OpenCode:** Desktop v2.0.24
**Ollama:** 0.40.0
**Статус:** 🛑 **СТОП для `qwen-coder-top`** — модель не умеет tool calls.
Найдена и **проверена** рабочая альтернатива. Конфиг оставлен чистым.

---

## Итог одной строкой

Механизм V2 работает — агент запускается, но `qwen-coder-top` вместо
вызова инструмента печатает JSON текстом, и инструмент не исполняется.
`qwen2.5:7b-instruct` в том же конфиге читает файлы корректно.

## 1. Тест tool calls: `qwen-coder-top` НЕ тянет

### 1.1 Почему тест сделан не так, как в задании

Задание предлагало проверить через `ollama run qwen-corer-top` в терминале
с просьбой «используй инструмент `read_file`». Такой тест не проверяет
tool calls: `ollama run` **не передаёт определения инструментов**, поэтому
модель не с чем работать и просто сочинит правдоподобный JSON. Результат
был бы одинаковым хоть с поддержкой, хоть без неё.

Проверка сделана через `/api/chat` с настоящим массивом `tools` — там видно,
превратился ли вызов модели в структурное поле `tool_calls` или остался
текстом.

### 1.2 Результат

Запрос: определение функции `read_file` + просьба прочитать `docs/version.json`.

| Модель | Структурный `tool_calls` | Что вернула в `content` |
|---|---|---|
| `qwen-coder-top:latest` | ❌ `null` | `{"name": "read_file", "arguments": {"path": "docs/version.json"}}` |
| `qwen2.5-coder:7b` (база) | ❌ `null` | то же самое |
| `qwen2.5:7b-instruct` | ✅ **есть** | пусто (модель не тратила текст) |

**Модель выдаёт правильный JSON — но в тексте, а не в поле `tool_calls`.**
Для агентного цикла OpenCode это равносильно отсутствию поддержки:
структурного вызова не пришло, значит инструмент не запустится.

### 1.3 Что исключено как причина

| Гипотеза | Проверка | Итог |
|---|---|---|
| Modelfile сломал модель | та же модель `qwen2.5-coder:7b` из базы | ❌ ведёт себя так же — не Modelfile |
| Шаблон не содержит `.Tools` | `ollama show --template` для обеих моделей | ❌ у обеих блок `.Tools` есть |
| Ollama не умеет tool calls в принципе | `qwen2.5:7b-instruct` | ❌ умеет — значит проблема в модели |
| Один случайный неудачный промпт | 3 независимые пробы: другой текст, другая схема параметров (`path` vs `filePath`), системная подсказка «always use the provided tools» | ❌ воспроизводится каждый раз |

Вывод: `qwen-coder-top` (и базовый `qwen2.5-coder:7b`) в связке с
Ollama 0.40.0 **не отдают структурные вызовы инструментов**.

### 1.4 Проверка через реальный subagent (A5)

Агент `local-fast` с `model: ollama/qwen-coder-top:latest` запущен
инструментом `subagent`. Сессия завершилась `state="completed"`, вывод:

```json
{"name": "read", "arguments": {"path": "C:\\analytics\\brain-25-evidence\\docs\\version.json"}}
```

Файл **не прочитан**, значение `app` **не получено**, ответ — сырой JSON.
API-тест предсказал ровно это, и нативный путь подтвердил.

## 2. Вывод и что дальше

**Стоп-условие сработало:** «Локальная модель не тянет tool calls → СТОП,
не настраивать». Дальше по плану с этой моделью идти незачем —
каждый делегированный вызов будет возвращать мусор вместо результата,
и это молча: агент завершится, ответ будет выглядеть правдоподобно.

**Но стоп относится к модели, а не к механизму.** И это важное различие:
идея рабочая, сломана конкретная модель.

### 2.1 Найдена и проверена альтернатива

`qwen2.5:7b-instruct` — та же архитектура Qwen2.5, та же машина, без
пересборки и без установки чего-либо.

Тот же агент, тот же вопрос, смена только модели:

| Вызов | Результат |
|---|---|
| `ollama/qwen-coder-top:latest` | сырой JSON, файл не прочитан |
| `ollama/qwen2.5:7b-instruct` | «The exact value of the "app" field … is "5.6.1"» |

Проверка на неугадываемость (значение `5.6.1` теоретически можно
выдумать, поэтому контрольный вопрос с нелогичными полями):

> Прочитать `docs/version.json`, назвать все ключи верхнего уровня,
> значения `data` и `tests`.

Ответ: 4 ключа (`app`, `data`, `audit`, `tests`), `data: 2026-09-25`,
`tests: 989`. Оба значения совпадают с реальным содержимым файла.
Модель не гадала — она вызвала инструмент и прочитала файл.

### 2.2 Что именно подтверждено рабочим

| Механизм | Статус | Доказательство |
|---|---|---|
| `agents.<name>.model` в `opencode.jsonc` | ✅ работает | агент зарегистрировался без перезапуска |
| Инструмент `subagent` с локальной моделью | ✅ работает | сессия создалась, `state="completed"` |
| Провайдер `ollama` без ручного конфига | ✅ работает | модель `ollama/...` резолвится, Ollama на 11434 |
| Tool calls у `qwen-coder-top` | ❌ не работает | 4 пробы, включая реальный subagent |
| Tool calls у `qwen2.5:7b-instruct` | ✅ работает | структурный вызов + верно прочитанный файл |

То есть **разведка из `DELEGATION_RESEARCH.md` подтвердилась полностью** —
механизм нативный и рабочий. Модель в нём была единственной преградой.

## 3. Конфиг: что сделано

### 3.1 `agents.local-fast` — добавлен, затем убран

| Шаг | Результат |
|---|---|
| Добавлен блок `agents.local-fast` | ✅ агент появился, запустился |
| Синтаксис | ✅ `ConvertFrom-Json` — OK |
| **Убран после провала `qwen-coder-top`** | ✅ `agents: (нет)` |

**Почему убран, а не оставлен.** Конфиг с заведомо нерабочей моделью
хуже отсутствия конфига: агент `local-fast` существовал бы, принимал бы
задачи, возвращал бы JSON вместо результата — и выглядел бы это как
«агент отвечает», а не как поломка. Откат оставлен с комментарием,
чтобы решение не потерялось и не пришлось искать заново.

### 3.2 Ручной провайдер `ollama` — удалять было нечего

Пункт B2 задания предполагал, что ручной блок `ollama` был добавлен
в прошлой задаче. **Не был.** Проверка:

```
'ollama' в конфиге: True   →   строка 149
149: "Path": "...;C:\Users\TshK\AppData\Local\Programs\Ollama;..."
```

Единственное вхождение слова — **PATH для запуска serena**, а не
провайдер модели. Блоков `provider`/`providers` в файле нет вообще.

Это согласуется с `GIT_MCP_SETUP.md` §7: пункт F («провайдер Ollama»)
там помечен как невыполненный. План F из того задания остаётся
**неактуальным**: V2 обнаруживает Ollama нативно, что и подтвердилось —
`ollama/qwen2.5:7b-instruct` заработал без единой строки конфига.

### 3.3 MCP не тронуты

После всех правок: `serena, context7, exa, playwright, duckdb, git` —
те же шесть серверов. Конфликта не возникло.

## 5. Рекомендация

### 5.1 Если локальная модель нужна

Закрепить `qwen2.5:7b-instruct` — изменение одной строки:

```jsonc
"agents": {
  "local-fast": {
    "description": "Лёгкий локальный исполнитель: поиск по коду, чтение файлов, первичный разбор.",
    "mode": "subagent",
    "model": "ollama/qwen2.5:7b-instruct"
  }
}
```

Модель уже установлена, ничего докачивать не нужно. Качество кода у неё
ниже, чем у coder-варианта, — для задач «найди / прочитай / перечисли»
это ровно тот случай, где разница несущественна.

### 5.2 Можно совместить

Если хочется именно `qwen-coder-top`, вариант — пересобрать её из
`qwen2.5:7b-instruct` вместо `qwen2.5-coder:7b` в `Modelfile`. Тогда
останется и coder-разметка, и рабочие tool calls. **Не проверено** —
это уже эксперимент, а не вывод из данных.

### 5.3 Чего не делать

| Не делать | Почему |
|---|---|
| Закреплять `qwen-coder-top` как агента | не исполняет инструменты, §1 |
| Ставить плагины делегирования | три из четырёх — V1, четвёртый требует OpenRouter (`DELEGATION_RESEARCH.md`) |
| Поднимать LiteLLM | встроенный `ollama` покрывает задачу, прокси лишний |
| Править SYSTEM в Modelfile ради tool calls | SYSTEM не участвует в разборе вызовов; дело в модели и парсере Ollama |
