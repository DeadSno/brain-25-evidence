### Три ошибки методики, найденные и исправленные

Первая версия скрипта давала неверные данные. Причины и решения:

1. **Все нули.** `page.evaluate(PROBE)` возвращал LCP/CLS/INP = 0, потому что `PerformanceObserver` асинхронен, а PROBE возвращался синхронно. → Разделено на два шага: `evaluate(INSTALL)` регистрирует обсерверы в `window.__cwv`, затем `wait_for_timeout`, затем `evaluate(READ)`.
2. **TTFB = 1–2 мс и bytes = 0** на второй и последующих страницах. Причина: service worker `docs/sw.js` отдаёт повторные визиты из кэша. → `browser.new_context(service_workers="block")` даёт честный холодный замер. **Это важно: без блокировки SW замеры нерепрезентативны.**
3. **FCP = 0** на части страниц — `getEntriesByName('first-contentful-paint')` ненадёжен при повторных навигациях на переиспользуемой странице. → `PerformanceObserver({type:'paint', buffered:true})`.

### Определения метрик

| Метрика | Как снимали |
|---|---|
| TTFB | `navigation.responseStart` |
| FCP | paint-observer, buffered |
| LCP | LCP-observer, buffered + LCP-элемент |
| CLS | сумма `layout-shift` без `hadRecentInput` |
| INP | максимум `event.duration` среди записей с `interactionId`, порог `durationThreshold: 16` |

**INP — лабораторный прокси, не полевая метрика.** Пассивно INP не измеряется. Для 5 ключевых страниц дополнительно синтезированы 4 цикла `mouse.move` → `click` → `Tab`. Значения ниже отражают реакцию на синтетическое взаимодействие, а не на реального пользователя.

## 4. Находки

Всего 4 находки. P0 нет.

### P1-1 · index.html весит 1045 KB и даёт худший LCP на сайте (480 мс)

**Факт.** Единственная страница с заметным LCP (480 мс против медианы 188 мс) и единственная с весом в мегабайт.

**Причина.** `index.html` подтягивает `docs/data.json` (**742 KB**) через `fetchJson('data.json')` в `docs/script.js:32`. Это самый крупный одиночный JSON в проекте и он грузится на главной.

**Смягчающее.** В `script.js` есть ленивая подгрузка `supplementsFullPromise` с комментарием «v5.6.2 (батч C, T4)» — то есть работа по разбивке уже начата в батче C. То есть находка частично пересекается с батчем C.

**Почему не P0.** 480 мс — это Good (порог 2500 мс), запас 5×. Влияния на ранжирование нет. Это оптимизация запаса, а не исправление дефекта.

### P1-2 · trends.html — единственная страница с CLS > 0.1

**Факт.** CLS = 0.1101 при пороге Good ≤ 0.1. Источник сдвига — `div#statCards.stat-cards`.

**Почему не P0.** 0.1101 < 0.25, то есть Poor не достигнут. Отклонение от Good минимальное. При этом trends.html — самая тяжёл��я страница (816 KB), и сдвиг вызван тем, что карточки статистики дорисовываются после загрузки данных.

## 8. Ограничения отчёта

- INP — лабораторный прокси на синтетических взаимодействиях, не CrUX-полевая метрика. Для вердикта по INP нужны данные из field data (RUM или CrUX API).
- Замеры — с одного региона, один раз, без повторов. Медианные значения устойчивы (разброс LCP 72–440 мс), но отдельные прогоны дадут отклонения.
- Кэш прогрев не моделировался: первый визит к холодному кэшу браузера может быть медленнее замеров.
- Service worker заблокирован намеренно. В сценарии возвращающегося пользователя метрики будут лучше, а не хуже.
