# ADR-001: Хранение в JSON, а не в БД

- **Статус:** Accepted
- **Дата:** 2026-09-25
- **Контекст:** Нужно выбрать способ хранения 130 карточек с вложенными структурами (mechs, interactions, key_sources).

## Решение

Хранить в одном файле `docs/data.json` (UTF-8, без BOM).

## Альтернативы

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **JSON-файл** | Простой, работает на GitHub Pages без сервера, версионируется git | Не масштабируется > 10 000 записей, нет запросов |
| SQLite | SQL-запросы, ACID | Не работает на GitHub Pages без сервера |
| PostgreSQL | Полноценная БД, оконные функции | Требует VPS, ~500 руб/мес |
| MongoDB | Гибкая схема | Избыточно для 130 карточек |

## Обоснование

1. **Размер:** 76 KB на 130 карточек → оценочно 60 MB на 100 000. JSON справится.
2. **GitHub Pages:** отдаёт статику бесплатно. БД потребует VPS.
3. **Версионирование:** каждое изменение видно в git diff.
4. **Клиент:** браузер парсит JSON за 30ms.

## Последствия

- ✅ Простая публикация без backend
- ✅ Git-история всех изменений
- ❌ Нет транзакций, параллельных записей
- ❌ Полная загрузка в память (для 130 ок, для 100k — нужна пагинация)

## Когда пересмотреть

При росте до **>5 000 карточек** — миграция на SQLite + API.

# ADR-002: GitHub Pages вместо VPS

- **Статус:** Accepted
- **Дата:** 2026-09-25

## Решение

Хостинг статики — **GitHub Pages**, BI — **Streamlit Cloud**.

## Альтернативы

| Вариант | Цена/мес | Плюсы | Минусы |
|---------|----------|-------|--------|
| **GitHub Pages** | 0 ₽ | Free, CDN, HTTPS, custom domain | Только статика |
| VPS (Hetzner) | 400 ₽ | Любой backend | Нужен админ, тьюнинг |
| Netlify / Vercel | 0 ₽ | Serverless функции | Лимиты bandwidth |
| AWS S3 + CloudFront | ~200 ₽ | Масштаб | Сложнее настройка |

## Обоснование

1. **Нулевая стоимость** на старте.
2. **Автодеплой** при push в main.
3. **HTTPS** и **CDN** из коробки.
4. **Streamlit Cloud** покрывает BI потребности бесплатно.

## Последствия

- ✅ 0 ₽ инфраструктура
- ✅ Deploy = git push
- ❌ Нет server-side логики (всё клиентское)
- ❌ Лимит 1 GB репо

## Когда пересмотреть

При необходимости **аутентификации**, **персональных данных** или **интеграции с БД**.

# ADR-003: Каскад EBI → NCBI для full texts

- **Статус:** Accepted
- **Дата:** 2026-09-25
- **Контекст:** EBI Europe PMC отдавал HTTP 500 на ~80% PMCID. Покрытие full texts — 81% (9074 из 11175).

## Решение

Каскадный fallback: сначала EBI, при 500 → NCBI efetch.

## Альтернативы

| Вариант | Результат |
|---------|-----------|
| Только EBI | 19% ok (плохо) |
| Только NCBI | Работает, но медленнее |
| **Каскад EBI → NCBI** | **99% ok (2229 из 2230)** |
| Retry EBI с backoff | 0% — сервер отдаёт 500 стабильно |

## Обоснование

1. EBI **быстрее** (один запрос), NCBI **надёжнее** (XML другого формата, но лояльнее к нагрузке).
2. Каскад даёт **best of both**: быстрый путь → медленный fallback.
3. Результат: **9 711 → 11 940** full texts (+23%).

## Последствия

- ✅ Покрытие 87% → 99.7% (от PMCID)
- ✅ +2866 full texts для анализа
- ❌ Дублирование логики в коде
- ❌ Разные форматы XML (но оба JATS-совместимые)

## Метрики

| Было | Стало |
|------|-------|
| 9 074 текста (81%) | 11 940 (99.7%) |
| 0 ok / 20 на втором запуске | 2229 ok / 2230 |

# ADR-004: Mermaid для диаграмм

- **Статус:** Accepted
- **Дата:** 2026-09-25

## Решение

Все UML/BPMN-диаграммы — в формате **Mermaid** (текст в Markdown).

## Альтернативы

| Инструмент | Плюсы | Минусы |
|------------|-------|--------|
| **Mermaid** | Текст в git, рендер на GitHub, редактируется в PR | Ограниченный набор нотаций |
| PlantUML | Полный UML | Нужен сервер рендера |
| draw.io | Красивые диаграммы | Бинарный формат XML |
| Visio | Индустриальный стандарт | Платный, бинарный |

## Обоснование

1. **Текстовый формат** → версионируется в git, диффится в PR.
2. **GitHub рендерит автоматически** — не нужен сервер.
3. **Редактирование в PR** — ревьюер видит changes.
4. **Экспорт в PNG/SVG** — через mermaid.live при необходимости.

## Последствия

- ✅ Диаграммы всегда актуальны (в коде)
- ✅ Ревью через git diff
- ❌ Не все нативные элементы UML (например, некоторые actor-стили)
- ❌ Не рендерится в VS Code без плагина

## Соглашения

- Файлы: `docs/architecture_diagrams.md`, `docs/bpmn_pipeline.md`
- Стили: без emoji в узлах (проблемы с рендером)
- Без `classDef` в mermaid (иногда ломает preview)

# ADR-005: Нормализация effect_tags через отдельный файл

- **Статус:** Accepted
- **Дата:** 2026-09-25
- **Контекст:** Поле `effects` в data.json содержит 160 уникальных текстовых значений на 130 карточек. Не подходит для фильтрации и графа.

## Решение

Ввести отдельный файл `docs/effect_tags.json` — нормализованные теги (18 категорий).

## Альтернативы

| Вариант | Проблема |
|---------|----------|
| Только `effects` (как было) | 160 уникальных → фильтр невозможен |
| Встроить теги в `data.json` | Смешение raw и derived данных |
| **Отдельный `effect_tags.json`** | Разделение источников правды |
| NER-модель для извлечения | Over-engineering для 130 карточек |

## Обоснование

1. **Разделение:** `effects` — свободный текст автора карточки. `effect_tags.json` — курированный словарь (18 тегов).
2. **Редактируется вручную** через `scripts/effect_tags_map.py` — контроль качества.
3. **Используется в графе** — стало основой для 1982 рёбер (ADR решает практическую проблему графа).
4. **Маппинг алфавитный** — легко поддерживать.

## Последствия

- ✅ 160 уникальных → 18 нормализованных
- ✅ Граф связей стал возможен
- ✅ Фильтр по тегам в UI
- ❌ Два источника правды (нужна синхронизация через `build_effect_tags.py`)

## Метрики

| Метрика | До | После |
|---------|-----|-------|
| Уникальных тегов | 160 | 18 |
| Рёбер в графе | 31 | 1982 |
| Работает фильтр | ❌ | ✅ |
