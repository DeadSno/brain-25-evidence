## ОРКЕСТРАТОР/ИСПОЛНИТЕЛЬ

P1. Оркестратор = НОВАЯ сессия на фазу. Саб-агент = один бриф.
    Старые чек-листы и сессии старше фазы закрываются без жалости.
P2. Промпт исполнителю — дословно:
    «Прочитай docs/briefs/<имя>.md и выполни его целиком в текущей ветке.
    Полный отчёт запиши в docs/reports/<фаза>.md: хэши, вывод pytest
    дословно, все замечания и нюансы. В чат верни ТОЛЬКО путь отчёта
    и топ-5 пунктов.»
P3. Память = файлы: отчёт в docs/reports/, состояние в docs/STATE.md.
    Резюме оркестратору запрещено заменять отчёт: тебе он передаёт
    путь + топ-5 + ДОСЛОВНЫЙ хвост pytest.
P4. Доверяй, но проверяй: после исполнителя оркестратор САМ гоняет
    pytest -q и e2e_smoke и прикладывает сырой вывод к докладу.
    «Исполнитель сказал зелёное» ≠ зелёное.
P5. Брифы коммитятся в main сразу при создании (это документы).
    Черри-пики брифов запрещены.
P6. Модель: оркестратор может быть дешевле/быстрее, исполнитель —
    самая сильная из доступных (в opencode.json настраивается per-agent).

P8. Параллельные задачи должны быть НЕЗАВИСИМЫМИ:
    - не трогают одни и те же файлы
    - не требуют результата друг друга
    - могут сливаться в main без конфликтов

P9. Параллельные исполнители работают в ОТДЕЛЬНЫХ ветках:
    - agent-A → v2.6.1-dev-part-a
    - agent-B → v2.6.1-dev-part-b
    - оркестратор мержит последовательно, решает конфликты сам
    - если конфликт неразрешим → стоп и доклад владельцу

P10. Параллельные тесты ЗАПРЕЩЕНЫ:
     - pytest/e2e гоняет ТОЛЬКО оркестратор после слияния всех веток
     - исполнители тестируют только свои изменения локально

P11. Параллельные коммиты в data.json ЗАПРЕЩЕНЫ:
     - data.json — критический файл, его меняет один агент за раз
     - контент-паки можно параллелить только если они в разные поля
       (один в interactions, другой в edu — ок; оба в edu — нет)

P13. Параллельные исполнители работают в ОТДЕЛЬНЫХ git worktree:
     оркестратор создаёт worktree на часть (git worktree add ../wt-a v2.7-dev-a),
     исполнитель стартует с путём своего worktree; мердж только оркестратор.
     Общий рабочий каталог для параллели запрещён (урок v2.7).
     P23 (усиление P21). reset --hard запрещён без страховки: сначала
    git branch backup-<дата> или git stash, потом reset. Второй убыток
    от этой команды = последний.
P24. КОММИТ ПОСЛЕ КАЖДОГО ЧАНКА. Незакоммиченная правка существует
    в среднем 40 минут — столько живёт до следующего reset/checkout.
    Панель opencode «Изменено файлов» не считается состоянием:
    состояние = git status в ТВОЁМ терминале.
P25. Предложения правок в opencode закрывать явно: Approve или Discard.
    Висячее предложение = мина: пересохранит бриф (+59-59) или уйдёт
    в случайный коммит.
P26. Одна сессия = один чанк. Чанки не смешиваются: новая задача —
    новая сессия. Это защищает от накопления контекстного шума и
    перекрёстных правок.
P27. Кодировка файлов: только UTF-8 без BOM. PowerShell Get-Content и
    git diff в консоли могут показывать кракозябры («╨╤╩╧») даже на
    здоровом файле — это иллюзия консоли, не порча. Оракул кодировки
    один: python decode('utf-8'). При реальном моджибейке — git restore
    и перезапись через VS Code (Ctrl+N → paste → Save As).
P28. Лимит OpenRouter free: при исчерпании суточной квоты чанк докручивается
    вручную владельцем (через VS Code) с точными REPLACE-парами от
    агента. Это не провал конвейера, а штатный сценарий.
P31. Агенту запрещено писать файлы через PowerShell-редиректы (>, >>,
    Out-File, Set-Content). Только инструмент write_file opencode или
    VS Code руками. Редиректы на Windows гарантируют моджибейк.
P32. Сниппеты «по памяти» запрещены. Любая правка чужого конвейера данных
    начинается с grep фактических имён (источник, формат точек, сигнатура).
    Урок чанка 2a: выдуманный priceHistory отклонён комментарием
    исполнителя — комментарий исполнителя = стоп-сигнал, а не шум.
P33. Коммит только после ВСЕХ зелёных гейтов: pytest + e2e + визуал.
    «Визуально красиво» не заменяет e2e: инварианты старых тестов
    ломаются именно тогда, когда дизайн меняется осознанно.
    Коммит раньше зелёного = amend, пока не запушен.
P34. Конвейер релиза работает: бриф → чанки → коммиты → документы →
    мердж → тег. Главное: каждый чанк атомарен (P24), каждый коммит
    зелёный (P33), каждая правка сверена с оракулом (P22).
P35. Релиз не заканчивается тегом: после push main+tag обязателен шаг
    деплоя Pages и проверка прода curl-ом титула. Урок v2.7.1: прод
    жил снимком ≤v2.6.0, пока владелец не посмотрел глазами.
    P35-доп: после каждого релиза проверять «счётчики в UI» — количество
    тестов, добавок, мета-анализов. Они устаревают быстрее кода.
