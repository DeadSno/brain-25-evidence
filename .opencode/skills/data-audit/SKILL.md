# Data Audit — 5 слоёв

Комплексный аудит данных brain-25-evidence: один скилл, 5 слоёв, один отчёт.

Создан 2026-10-03 взамен `data-quality-auditor`, который работал только с CSV
и на нашем JSON давал бессмысленный DQS.

---

## Правило верификации находок

**Находка без команды, которая её воспроизводит, — не находка.**

Для каждого пункта в отчёте обязательно:

1. команда или запрос, дающий число;
2. это число — до и после того, как находка появилась (для регрессий);
3. список конкретных записей, не только количество.

Если число не удалось воспроизвести — пишем «не подтверждено», а не выдумываем.

Особенно это касается слоя 3: **`data/db/brain.duckdb` может быть занят
работающим процессом** (в нашей среде — `node.exe`), и прямой `duckdb.connect`
тогда падает с `WinError 32`, а `shutil.copy2` тоже. Запрашивать БД лучше
через MCP-инструмент `query_duckdb` — он открывает файл read-only и работает.

---

## Лимит находок

Ориентир — **60** на полный прогон всех 5 слоёв.

Больше 60 — значит либо сломан слой целиком (тогда одна находка на слой), либо
идёт перебор косметики. Сначала P0/P1, P2 — только если кончились.

Не генерировать находку на каждую запись: «48 карточек без `hedges_g_ci`» — одна
находка со списком, не 48 находок.

## Слой 1 — `data.json`, источник правды

- **Completeness** — пустые строки, `null`, `[]`. Ориентир: `hedges_g` 45,
  `hedges_g_ci` 48, `ma_top3` 50, `citations` 18
- **Consistency** — типы. `grade` ∈ {A,B,C,D}; `scienceIndex` int;
  `updated` — ISO `YYYY-MM-DD`
- **Uniqueness** — дубли по `id` и по `title`
- **Validity** — `hedges_g_pmid` по `^\d+$`, DOI по `^10\.\d{4,}/\S+$`
- **Distribution** — `grade`, `category`, `effects`
- **Outliers** — см. предупреждение ниже

### Две проверки, которые нельзя писать «по привычке»

**Категории.** Поля `category` — **79** уникальных значений вида
`Неврология/Метаболизм`, а не 8 категорий. Схемы из 8 корней в репозитории
нет (`CATEGORIES` встречается только в посторонних скриптах). Проверять надо
согласованность формата «путь через `/»», а не соответствие списку из 8.

**3σ по `scienceIndex`.** Распределение 2…10666, среднее 1235.42, σ 2021.99.
Порог μ+3σ = 7301.39 даёт **ровно 4 записи** — `Омега-3`, `Витамин D`,
`Пробиотики`, `Калий`. Это четыре крупнейших вещества, то есть выбросы
ожидаемые и правильные. Фильтр «3σ» здесь не находит плохих данных — он
находит большие вещества. Как гейт он бесполезен; как отчёт «4 выброса, все
легитимны» — полезен.

## Слой 2 — производные

| Файл | Контракт |
|------|----------|
| `docs/data_index.json` | `{_meta, supplements}`, `supplements` = 130 |
| `docs/api/v1/supplements.json` | `{version, generated_at, count, license, source, site, schema, supplements}`, `supplements` = 130 |
| `docs/effect_tags.json` | 130 ключей (id вещества) → список тегов |

Проверять:

- `data_index.supplements` = 130 и по тем же `id`, что `data.json`, **в том же
  порядке** — от расхождения порядка ломается всё, что строит индекс
- `supplements.json.count` совпадает с `len(supplements)`
- `generated_at` не старше `data.json`
- 18 тегов в `effect_tags.json` **канонические** — это словарь `effect_tag`
  в DuckDB; проверять, что множества совпадают, и что нет тегов-сирот
- теги в `data.json.effects` ⊆ канонических

Это контракт **производных файлов**, а не API-контракт — см. «Чего НЕ делать».

## Слой 3 — DuckDB

### Структура, которую надо знать до запросов

`paper` — **глобальный корпус** (37 618 статей) и `supplement_id` в ней
**нет**. Связь статей с веществами лежит в отдельной таблице:

```
key_source(supplement_id, pmid, doi, title, year, journal)   393 строки
```

Остальные таблицы: `supplement` (130), `mech` (391, по `supplement_id`),
`interaction` (199), `supplement_tag` (226), `effect_tag` (18, словарь тегов),
`coi` (6310, по `pmid`).

Отсюда две ошибки, которых надо избежать:

- искать `paper без supplement` — такого поля нет; правильная проверка
  `key_source.pmid` без строки в `paper`;
- считать дубли по `(supplement_id, paper_id)` в `paper` — поля нет; правильная
  пара `(supplement_id, pmid)` в `key_source`.

### Базовые значения

| Проверка | Значение |
|----------|---------:|
| `supplement` | 130 — совпадает с `data.json` |
| `key_source.pmid` без `paper.pmid` | **190** |
| `key_source` без `supplement` | 0 |
| `mech` без `supplement` | 0 |
| `interaction` без `supplement` | 0 |
| `supplement_tag` без `supplement` | 0 |
| `coi.pmid` без `paper.pmid` | 0 |
| `effect_tag` без `supplement_tag` | 0 |
| дублей `key_source(supplement_id, pmid)` | 0 |
| `supplement.citations` NULL или 0 | 18 — совпадает с `data.json` |

**`paper` без `key_source` — 37 420, и это нормально.** `paper` накапливает
корпус целиком, статья может существовать без привязки к веществу. Считать
это орфаном нельзя.

### Годы в `paper`

Проверять «год вне 2000-2026» **нельзя**:

- `year < 2000` → **4 729** записей, минимум **1926**. Это легитимная
  старшая литература, а не битые данные
- `year` NULL → **6**
- `year > 2026` → **5** (2027 год — вот это уже подозрительно)
- диапазон: 1926…2027

Корректные проверки: `year IS NULL` и `year > текущий год`.

## Удаление и упрощение

Отчёт — **один файл**, не пять.

Что убрано из первоначальной идеи пяти отдельных отчётов:

- пять отчётов → один, слои = разделы
- «профиль датасета» с MCAR/MAR/MNAR → не применимо: данных ровно столько,
  сколько карточек на сайте, пропуски здесь не «механизм ответа»
- отдельный скрипт профилирования → не нужен, 130 записей читаются за секунды

Что добавить при следующем прогоне:

- сверка `order` в `data_index` с `data.json` (в базовой линии не проверялось)
- `verdict`: в DuckDB это **строка** (`работает` 40 / `зависит от контекста` 64 /
  `не подтверждено` 26), а не число −1/0/1 — контракт надо описать, иначе
  слой 3 и слой 1 будут считать одно и то же по-разному
- `code` в `supplement`: диапазон −1…1, всего **3 уникальных** значения

## Чего НЕ делать

- **Не проверять CSS и HTML.** Оформление — не данные. Для этого
  `ui-ux-deep-audit` и `visual-design-audit`
- **Не проверять тесты** и не запускать `pytest`. Здесь нечего утверждать о
  покрытии — это `qa-deep-audit`
- **Не проверять API-контракт.** Слой 2 проверяет контракт
  *производных файлов* (`version`, `count`, `schema`, состав `supplements`) —
  это про целостность данных, а не про HTTP-эндпоинты
- Не чинить данные молча: скилл только читает и предлагает
- Не выгружать PMID/DOI в отчёт без нужды — сайт о здоровье
- Не запускать слой 5 без `RUN_EXTERNAL=1`
- Не открывать `brain.duckdb` прямой коннект, пока файл занят другим процессом
