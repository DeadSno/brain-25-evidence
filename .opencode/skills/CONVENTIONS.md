## Работа с worktree

- Все коммиты — **только в main checkout** (`C:\analytics\brain-25-evidence`).
- worktree — только для временных экспериментов, удалять после.
- Причина: detached HEAD теряет коммиты (`witty-nebula-2`, `misty-mountain`, `stellar-river`).

Проверено 14.10.2026: 58 worktree, из них **три с непривязанными коммитами** —
`curious-star-2` (6), `witty-nebula-2` (3), `misty-mountain` (1). Их HEAD не
достижим ни из одной ветки и ни из `origin`, они живут только ref'ом
`refs/worktrees/*/HEAD`. `git worktree prune` или `git gc` — и коммиты пропадут
вместе с ветками сессий. Перед удалением worktree:

```
git -C <main> merge-base --is-ancestor <worktree-HEAD> v5.6.5-dev
git -C <main> diff origin/v5.6.5-dev <worktree-HEAD> --stat
```

Ненулевой код возврата у первой = коммиты ещё не в ветке, **но только если
вторая пуста**. Cherry-pick переписывает хеши, и тогда первая даёт ложную
тревогу, а вторая доказывает, что дерево уже совпадает — подробности в
«Ложное срабатывание проверки после cherry-pick». Решает вторая строка.

### Push сразу после cherry-pick

После `cherry-pick` — **пушить немедленно**, не откладывая до конца
задачи. Прецедент 15.10.2026: 6 коммитов (`5a6e219` … `9a336cc`) провисели
локально ~10 минут после `Merge origin/v5.6.5-dev into v5.6.5-dev`; всё это время
ветка была `ahead 6`, и следующая задача исходила из неверного числа
коммитов. Cherry-pick — это операция с чужими коммитами: пока они не в
`origin`, следующий `merge origin/...` может их затронуть.

пустым** — и `git worktree list` его больше не показывает, поэтому число в
списке не меняется и мусор не виден. Проверено 15.10.2026: 56 worktree в
списке, но на диске лежали 6 пустых каталогов (`clever-nebula`,
`cosmic-falcon`, `curious-otter`, `curious-star-2`, `shiny-orchid`,
`stellar-river`) — 0 элементов, без метаданных в `.git/worktrees`.

### Push из detached HEAD

Ветка может быть занята другим чекаутом (`git worktree list` показывает её
с префиксом `+`). Тогда локально сдвинуть её нельзя, а пушить надо — пуш
работает по refspec и указатель ветки не трогает:

```
git push origin HEAD:v5.6.5-dev   # fast-forward, только remote
```

Локальная ветка в главном чекауте после этого отстаёт; догонять её
отдельным `merge --ff-only` по явному разрешению.

- ПРАВИЛО: **после каждого батча** — cherry-pick в main + push + проверка
  `branch --contains` (прецедент 7 — `playful-canyon-2`, 13A1, 16.10.2026).
  Формулировка «перед закрытием сессии» слабее: между батчами сессия может
  не дойти до конца, и тогда коммиты остаются жить только в
  `.git/worktrees/<name>/HEAD`.
- Проверка после каждого батча:
  ```
  git worktree list
  ```
  для каждого: `git -C <wt> log v5.6.5-dev..HEAD --oneline`
  Пусто → safe. Не пусто → **не повод сразу cherry-pick'ить**: сперва
  `git -C <main> diff origin/v5.6.5-dev <wt-HEAD> --stat`, пусто → уже забрано
  (следующий раздел).
- Отдельный случай — батч, который ещё ни разу не забирали. Тогда HEAD
  worktree не принадлежит ни одной ветке:
  ```
  git -C <main> branch --contains <wt-HEAD>
  git -C <main> diff origin/v5.6.5-dev <wt-HEAD> --stat
  ```
  ⚠️ Вывод `branch --contains` читается **только в паре** с `diff`:
  пусто + diff пусто → уже забрано (ложный сигнал, следующий раздел);
  пусто + diff **не** пусто → detached, нужен cherry-pick. Пустое
  `branch --contains` **само по себе не доказывает** detached: после
  cherry-pick хеш переписан, и проверка молчит ровно так же.

### Ложное срабатывание проверки после cherry-pick

⚠️ После `cherry-pick` хеши коммитов **меняются** — переписывается committer
timestamp. Поэтому `git -C <wt> log v5.6.5-dev..HEAD` покажет коммиты даже
после того, как их содержимое уже в ветке и запушено.

Проверено 15.10.2026: батч 10 жил в `sunny-canyon` как `f4ea752 … eb47cf4`
(родитель `f4ea752` = `06ca148` = HEAD `v5.6.5-dev` в тот момент). После
`cherry-pick` в `v5.6.5-dev` получилась параллельная история `44a66b3 … bcbce7a`,
и проверка выше дала ложное «6 непушенных коммитов».

Содержимое при этом не потеряно — совпадало дерево:

```
git diff origin/v5.6.5-dev eb47cf4   # пусто
git diff v5.6.5-dev HEAD             # пусто
```

**Решающий критерий — сравнение деревьев, а не список коммитов.**
Сверять хеши нельзя: перед удалением worktree, который уже cherry-picked,
`git log v5.6.5-dev..HEAD` будет непустым, и это нормально.

То же касается `git branch --contains`. Замерено 16.10.2026 на
`eager-circuit` (`61cc177`, cherry-picked как `8ada05d`): ветка не найдена,
хотя содержимое в `origin` уже есть. Отличие от `log` в том, что эта
проверка молчит и для настоящего detached-состояния, поэтому годятся
только в паре с `diff`:

| `branch --contains` | `diff origin/v5.6-dev` | Вывод |
|---|---|---|
| пусто | пусто | cherry-picked, содержимое в origin — забирать нечего |
| пусто | не пусто | detached и не забрано — нужен cherry-pick |
| `* v5.6-dev` | пусто | обычное состояние, всё в ветке |

Контроль на тот же момент: `git branch --contains 76b3ce1` (база, не
cherry-pick'илась) → `* v5.6.5-dev`, и `merge-base --is-ancestor 61cc177
v5.6.5-dev` → exit 1 на уже забранном коммите.

## Pre-commit порядок генераторов

Хук лежит в `.githooks/`, а не в `.git/hooks/` — в worktree `.git` это
файл-указатель. Актуальный путь: `git rev-parse --git-path hooks`.
Замерено 14.10.2026.

Порядок важен: **генераторы идут до pytest**. Обратный порядок даёт гейту
сравнить устаревшие артефакты с кодом и завалить коммит, который сам же
эти артефакты и обновил бы.

| # | Шаг | Команда | Что делает |
|---|---|---|---|
| 1 | Sitemap | `python scripts/build_sitemap.py --commit-date` | пишет `docs/sitemap.xml`, сам делает `git add` |
| 2 | Junk guard | `git ls-files -- docs reports` + regex | ловит `_*_tmp_*`, `_*_diag_*`, `_*_baseline_*` |
| 3 | Feed | `python scripts/build_feed.py --commit-date` | пишет `docs/feed.xml`, сам делает `git add` |
| 4 | Тесты | `pytest -q -m "not network and not snapshot_data and not (snapshots or a11y or tabs or graph or mobile375 or e2e)" -k "not real_docs_sitemap_is_current and not live_docs_feed_is_current"` | exit ≠ 0 → коммит прерван. Фильтр `not (snapshots or …)` не даёт хуку гонять браузерные маркеры — полный прогон ~8–10 минут; подстроку `not network and not snapshot_data` требует `test_precommit_hook.py` |

- `--commit-date` обязателен. Без него генератор ставит дату запуска, и гейт
  «artefact is stale» срабатывает сам на себе.
- Шаги 1 и 3 добавляют свои файлы в индекс сами — повторно добавлять не нужно.
- Хук добавляет в индекс **только** эти два файла. Если правка документации
  или сборка изменили что-то ещё, это уедет в коммит незамеченным — смотреть
  `git status` перед `git commit`.
- Коммит «только `reports/*.md`» не всегда остаётся таким: сборка может
  переписать `sitemap.xml` / `feed.xml`. Проверять `git show --stat`.
- Руками генераторы без `--commit-date` не запускать — перепишут `lastmod`,
  и следующий чужой коммит станет ложным «устареванием».
- Генераторы без `__main__`-guard опасны при импорте: `build_changelog_public.py`
  пишет `docs/changelog_public.html` на импорте (QA-P2-05). Правка таких
  скриптов — сначала guard, потом всё остальное.

## Бамп кэша style.css (`?v=` и `CACHE_VERSION`)

Правка `docs/style.css` не доезжает до браузера сама: страницы подключают
`style.css?v=NNN`, и при неизменном NNN возвратные посетители получают файл из
кэша. Поэтому правка CSS = бамп четырёх точек сразу:

1. `style.css?v=NNN` — во **всех** 143 файлах со `<link>` (`docs/*.html` +
   `docs/sup/*.html`; из 147 файлов ссылку не держат `atlas.html`,
   `graph.html`, `offline.html`, `google*.html`), значение обязано остаться единым. Замена — **литеральная**
   (`str.replace('style.css?v=429', 'style.css?v=430')`), не regex по разметке:
   см. «Правила безопасности» в `AGENTS.md`.
2. `tests/_style_version_baseline.txt` — то же число, руками.
3. `docs/sw.js` — `var CACHE_VERSION` плюс комментарий прямо над ним в формате
   `/* Бамп vN -> vM <причина> */`; без него `CACHE_VERSION` не почистит старый
   `-static`-кэш.
4. `templates/sup.html.j2` и `templates/sup_index.html.j2` — тот же
   `<link … style.css?v=NNN>`. Пропущенный шаблон не видно ни в браузере, ни в
   хуке: следующая перегенерация `scripts/build_sup.py` откатывает номер сразу
   на всех 131 странице `docs/sup/*.html` (`test_build_sup_idempotent.py`
   помечен `snapshot_data` и в хуке не гоняется). Рассинхрон случался четыре
   раза: v413/414, v423/425, v425/429, v429/430 (13C).

Гейт — `tests/test_style_version_bump.py` (5 тестов): единая версия во всех
страницах, совпадение с baseline, непустая причина у `CACHE_VERSION`, отсутствие
отката, совпадение `?v=` в `templates/*.j2` с версией страниц. Комментарий ищется регуляркой `CACHE_COMMENT` от **первого** совпадения,
поэтому новую запись вставляют непосредственно над `var CACHE_VERSION`, а старое
значение в коде поднимают.

**Сколько раз бампать за сессию — вариант А (принят владельцем 16.10.2026).**
Если за одну сессию правок `style.css` несколько (13C1/13C2/13C3 и т.п.) —
**бампать один раз**: первый коммит с правкой CSS поднимает `?v=` и
`CACHE_VERSION`, остальные коммиты правят только `style.css`. Вариант Б
(бампать каждую правку) отвергнут: он гоняет 143 файла на каждый коммит, не
меняя для пользователя ничего — обе версии уезжают одним push, а кэш
инвалидируется один раз.

Оговорка: между коммитами сессии (до push) у пользователя, загрузившего сайт из
промежуточного состояния, останется старая копия под тем же `?v=`. Окно
маленькое. Если правки разнесены по времени (дни) — бампать каждую (вариант Б).

Не путать с `version.js?v=NNN` — отдельная шкала, её поднимает хук.

## Медиазапросы в `docs/style.css` — только `max-width`

Перемерено 16.10.2026 (13C): в `docs/style.css` **42 `@media`**, из них по
ширине — **15**, и все пятнадцать заданы через `max-width`. `min-width`
встречается ровно один раз — `@media (min-width: 621px) and (max-width: 1200px)`
(лента шапки, MOB-P2-14), и там он уместен по смыслу: это диапазон, а не
«широкий» вариант.

Это не долг, а устройство файла: CSS написан **mobile-last** — базовые правила
обслуживают широкий экран, а каждый `@media` блок есть узкий оверрайд
(шапка в сетку, сайдбар в нижнюю шторку, легенда атласа, cookie-баннер).
Добавлять `min-width` «для симметрии» не нужно: он развернул бы логику.
Находка вида «в файле 0 `min-width`» — ложная; проверять надо не форму
запроса, а то, делает ли блок узкий оверрайд.

Раньше браузерные маркеры (snapshots, a11y, tabs, graph, mobile375, e2e)

### Обновление эталонов (UPDATE_SNAPSHOTS)

Гейт `RUN_SNAPSHOTS` удалён в v5.6.5 — от переменных скип больше не зависит.
Нужна только переменная перезаписи:

```powershell
$env:UPDATE_SNAPSHOTS="interactions-412,interactions-1280"
pytest -q -m snapshots -k interactions
```


Разделитель списка — **запятая**, не `;` (`_parse_update`,
`test_visual_snapshots.py:131`). При `;` режим молча остаётся `off`: тесты
не скипаются, а **падают** на сравнении с эталоном — вывод при этом выглядит
как обычная регрессия пикселей, и причина неверная. Проверено 15.10.2026.

Имя эталона — `имя-ширина` (`interactions-412`), без браузера: суффикс
`chromium`/`webkit` в каталоге добавляется автоматически, в переменной он
не нужен и не должен совпадать.

## MCP-серверы

Актуальные имена: `context7`, `playwright`, `git`, `codebase-memory`, `serena`.

- **НЕ `mcp__playwright__*`.** Это формат MCP V1. В V2 инструменты плоские:
  `playwright.browser_navigate`, `playwright.browser_evaluate`,
  `playwright.browser_click`. Префикс `mcp__<server>__` в именах инструментов
  не используется.
- Блок `mcp` в `opencode.json` проекта отсутствует — серверы настраиваются
  глобально. Проверять фактический список — по каталогу инструментов сессии,
  а не по конфигу.

### Git MCP: read — MCP, write — shell

Разделение **правилом, а не блокировкой**: технически отключить write-тулы
git MCP на этой машине нельзя (см. «Почему нет блокировки»).

- **read — MCP:** `git_status`, `git_log`, `git_diff`, `git_diff_staged`,
  `git_diff_unstaged`, `git_show`, `git_branch`. Вызываются свободно.
- **write — shell:** `git add`, `git_commit`, `git_checkout`,
  `git_create_branch`, `git_reset`. Только по явной команде владельца
  в задании. `git_reset` и `git_checkout` — не вызывать даже в общем
  виде «приведи репозиторий в порядок».
- `git_push` в MCP **не существует** — всего 12 тулов, 7 read + 5 write.

#### Почему нет блокировки

Проверено 2026-10-12 на `opencode.jsonc` + бинарниках обоих рантаймов.
Конфиг читают **два** рантайма: Desktop 2.0.24 (V2) и CLI 1.18.35 (V1),
и механизмы отключения у них взаимоисключающие.

| Механизм | V1 CLI | V2 Desktop |
|---|---|---|
| `mcp.<name>.tools: {...}` | поля нет в схеме | поля нет в схеме |
| top-level `"tools": {...}` | работает | молча игнорирует |
| top-level `"permissions": [...]` | ломает `mcp list` | работает |

- `mcp.<name>.tools` **не существует ни в одной версии**. В V1 zod-схема
  `McpLocalConfig` = `{type, command, cwd, environment, enabled, timeout}` —
  поля `tools` нет, ключ отбрасывается. Запись такого вида — no-op.
- Оба варианта со `tools`/`permissions` ломают другой рантайм: `permissions`
  уже ломал V1 CLI в этом репозитории, поэтому его не повторяем.

Вывод: разделение держится на дисциплине агента и на этом разделе,
а не на конфиге. `permissions` из «Правил безопасности» MCP-вызовы
не покрывают — ограничивает только этот раздел.
