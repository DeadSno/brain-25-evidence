## Как проверять

- Скиллы **НЕ хардкодят** эти числа.
- Каждый скилл читает актуальное значение динамически
  (grep, ls, `pytest --collect-only`) при запуске.
- Таблица выше — ориентир для человека, а не значение для отчёта. Число в
  отчёте скилла берётся командой из колонки «Как проверить», а не отсюда.
- Часть счётчиков продублирована в `docs/version.json` (`app`, `data`, `audit`,
  `tests`). Это машиночитаемый источник для скриптов, но он покрывает не все
  числа — CSS, SW и структуру из него не взять.

## Правила скиллов

1. Никаких стоп-дат («актуально на 2026-09-30»).
2. Числа — динамически из репо.
3. Один скилл = одна задача.
4. Ссылки только на актуальные документы.
5. НЕ дублировать `reports/AUDIT_MASTER.md` — он источник правды по находкам.
6. Максимум ~250 строк на скилл.
7. Правило верификации: любой вывод подтверждать замером.

## Правила проекта

- На каждой странице в `.actions` нет ссылки на себя; единый набор кнопок
  на основных страницах.
- Футеры страниц байт-идентичны.
- Тема — через `html.dark` + `body.dark`.
- Тесты перед коммитом обязательны.
- Файлы >30 строк — только через Python (PowerShell heredoc ломает backticks).

## MCP-серверы

Актуальные имена: `context7`, `playwright`, `git`, `codebase-memory`, `serena`.

- **НЕ `mcp__playwright__*`.** Это формат MCP V1. В V2 инструменты плоские:
  `playwright.browser_navigate`, `playwright.browser_evaluate`,
  `playwright.browser_click`. Префикс `mcp__<server>__` в именах инструментов
  не используется.
- Блок `mcp` в `opencode.json` проекта отсутствует — серверы настраиваются
  глобально. Проверять фактический список — по каталогу инструментов сессии,
  а не по конфигу.

### Git MCP: read — MCP, write — shell

Разделение **правилом, а не блокировкой**: технически отключить write-тулы
git MCP на этой машине нельзя (см. «Почему нет блокировки»).

- **read — MCP:** `git_status`, `git_log`, `git_diff`, `git_diff_staged`,
  `git_diff_unstaged`, `git_show`, `git_branch`. Вызываются свободно.
- **write — shell:** `git add`, `git_commit`, `git_checkout`,
  `git_create_branch`, `git_reset`. Только по явной команде владельца
  в задании. `git_reset` и `git_checkout` — не вызывать даже в общем
  виде «приведи репозиторий в порядок».
- `git_push` в MCP **не существует** — всего 12 тулов, 7 read + 5 write.

#### Почему нет блокировки

Проверено 2026-10-12 на `opencode.jsonc` + бинарниках обоих рантаймов.
Конфиг читают **два** рантайма: Desktop 2.0.24 (V2) и CLI 1.18.35 (V1),
и механизмы отключения у них взаимоисключающие.

| Механизм | V1 CLI | V2 Desktop |
|---|---|---|
| `mcp.<name>.tools: {...}` | поля нет в схеме | поля нет в схеме |
| top-level `"tools": {...}` | работает | молча игнорирует |
| top-level `"permissions": [...]` | ломает `mcp list` | работает |

- `mcp.<name>.tools` **не существует ни в одной версии**. В V1 zod-схема
  `McpLocalConfig` = `{type, command, cwd, environment, enabled, timeout}` —
  поля `tools` нет, ключ отбрасывается. Запись такого вида — no-op.
- Оба варианта со `tools`/`permissions` ломают другой рантайм: `permissions`
  уже ломал V1 CLI в этом репозитории, поэтому его не повторяем.

Вывод: разделение держится на дисциплине агента и на этом разделе,
а не на конфиге. `permissions` из «Правил безопасности» MCP-вызовы
не покрывают — ограничивает только этот раздел.
