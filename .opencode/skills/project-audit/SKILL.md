# Инструкция по полному аудиту

Триггер: пользователь просит "проведи аудит проекта" или "полное ревью".


## Правило верификации находок

Прежде чем фиксить находку — воспроизведи её:
- mobile: реальный viewport в Playwright
- touch: getBoundingClientRect() с реальным кликом
- тест: мутация (сломать → тест падает)
- JS: node --check + реальный прогон
- данные: запрос к файлу, не к памяти

Если не можешь воспроизвести — находка не подтверждена,
в отчёт идёт со статусом «требует верификации».

Не «починил бы» и не «добавил бы clearRect на всякий случай» — сначала
воспроизвёл. В QA-аудите этого проекта **5 находок из 42** оказались ложными,
и все пять я бы выдала как критичные: `cv.width = ...` уже чистит canvas,
`Рёбер` не есть мозгибаки, `lib/` жив и нужен генератору отчёта.



## Лимит находок
Ориентир — 60 в отчёте. При превышении:
- группировать однотипные (130 звёзд = 1 находка, не 130)
- P0/P1 — не резать никогда
- P2 — сжимать до паттернов
Число в отчёте — что нашлось, а не что влезло.

## Чек-лист из 12 проверок

### 1. Структура проекта
- Дерево верхних 3 уровней (исключая .venv, node_modules, .git, __pycache__)
- Файлы вне логичных папок
- Пустые папки

### 2. Устаревшие данные
Найди вхождения чисел: 103, 113, 94, 9074, 5135, 10759
Найди устаревшие версии: v3.6, v3.5, v3.4, batch 16, batch 17a
Формат вывода: файл:строка — найдено "103 добавки" — заменить на "130 добавок"

### 3. Мёртвый код
- Файлы .py в scripts/ без упоминаний в .md
- Функции внутри файлов без вызовов
- Импорты в начале файла, которые не используются

### 4. Дубли данных
- Сравни docs/data.json vs docs/api/v1/supplements.json (количество, поля)
- Сравни docs/data.json vs data/db/brain.duckdb (если БД есть)
- Проверь reports/ на старые версии отчётов

### 5. Битые файлы
- JSON-файлы невалидные (проверить через python -m json.tool)
- Файлы меньше 100 байт (кроме __init__.py)
- Пустые .md файлы
- Файлы с _test, _old, _bak, _tmp в имени

### 6. Зависимости
- Что в requirements.txt не используется в коде
- Что используется в коде, но отсутствует в requirements.txt
- Устаревшие версии (2+ года без обновлений)

### 7. Синхронизация документации
- Ссылки в .md на несуществующие файлы
- docs/glossary.md vs реальные термины в коде
- docs/data_dictionary.md vs реальные поля в data.json
- Упоминания версий (должны совпадать с текущей)

### 8. Безопасность
- Поиск по проекту: ключи API (exa, openai), пароли, токены, Bearer-токены
- Проверка .gitignore (что нужно добавить)
- Проверка какие файлы уже в git что не должны быть

### 9. Mermaid-диаграммы
- Найди все Mermaid-блоки в .md
- Проверь парность backticks (чётное число)
- Найди блоки с пустым содержимым

### 10. Большие файлы
- Файлы больше 10 MB в проекте (кроме .venv, node_modules)
- Файлы больше 100 MB в git LFS или основных папках
- Размер .git/ если доступен
- Глубокий разбор размера и план очистки (top-10, `data/journals/`,
  `tests/snapshots/`, `docs/sup/`, `_tmp_*`) — делегировать скиллу
  **repo-size-audit**; здесь только флаг «есть крупное», без плана удаления

### 11. Версионирование
- Текущая версия в docs/version.json
- Совпадает ли с последним тегом git
- Упоминания версии в README, ARCHITECTURE, остальных файлах

### 12. Тесты
- Все ли test_*.py содержат хотя бы 1 test_
- Пропущенные тесты (pytest.mark.skip)
- Тесты без assert

## Формат отчёта reports/AUDIT_REPORT.md

Отчёт должен содержать:

1. Шапка: AUDIT REPORT — brain-25-evidence, дата, автор (OpenCode)
2. Резюме: всего проверок 12, найдено проблем X, критичных Y, средних Z, мелких W
3. По каждому из 12 пунктов — раздел с находками или "чисто"
4. Раздел 9. Рекомендации — три уровня приоритета: критично / важно / можно отложить

Начни с резюме, потом по каждому пункту. Если пункт чист — пиши "чисто".

## Локаль: RU + EN (обязательно для всех проверок)

Проверять в обеих локалях: RU (`lang="ru"`) и EN (`localStorage.lang='en'`).
Оба языка — столпы проекта, ни один не второстепенный. Каждая проверка выше
выполняется дважды — в RU и в EN; находку помечать локалью `RU` / `EN` / `RU+EN`.

| Локаль | Как включить | Откуда текст |
|---|---|---|
| RU | по умолчанию, `<html lang="ru">` | словарь `docs/i18n.js` (`I18N.ru`), данные — `docs/data.json` |
| EN | `#langSelect` или `localStorage.setItem('lang','en')` + перезагрузка | `docs/i18n.js` (`I18N.en`) + `docs/data_en.json` (паритет 130/130) |

- `docs/i18n.js` выставляет `document.documentElement.lang = LOCALE`;
  статический `<html lang="ru">` на всех страницах — это долг SEO-01, а не
  признак того, что RU главнее
- Переводятся атрибуты `data-i18n`, `data-i18n-text`, `-title`, `-alt`,
  `-aria-label`, `-placeholder`, `-tooltip`, `-vars`
- В EN не должно остаться кириллицы в интерфейсе (гейт
  `tests/test_i18n_no_russian.py`); русская строка в EN — находка
- Пока перевод не применён, `<html>` держит класс `i18n-pending`
  (`html.i18n-pending main{visibility:hidden}`) — проверять, что класс
  снимается и контент не остаётся скрытым
- Находка «только в RU» или «только в EN» — это находка, а не норма

Паритет `docs/data.json` ↔ `docs/data_en.json` (130/130) —
обязательная проверка в разделе дублей данных.

- Словарь `docs/i18n.js` должен покрывать обе локали.
